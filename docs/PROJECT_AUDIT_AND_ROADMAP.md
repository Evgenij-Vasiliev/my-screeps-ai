**Что реально работает (по коду):**

- Ядро тонкое, вся комнатная логика — в Room Manager; каждая подсистема обёрнута в try/catch в `empire.js` (16 `console.log` — все внутри catch).
- Task System работает по зафиксированной в `docs/TASK_SYSTEM_ARCHITECTURAL_FOUNDATION.md` схеме: потребность → Task → FIFO → Worker → Executor, без scheduler/dispatcher/assignmentEngine. Task не удаляется при выдаче, идентичность потребности — по полям задачи, резервация через `reservedBy` с автоматическим «освобождением» после смерти крипа (`task.manager.js:85`).
- Тяжёлые кэши (structure/mineral/defense/remote/attacker) перенесены из Memory в `global` (`scanner.js`, `empire.js:17-33`) — это был большой выигрыш против JSON-сериализации сотен ID.
- Traveler интегрирован в 14 модулях (57 вызовов `travelTo`), `moveTo` остался только в тактическом шаге атакующего (`defense.attacker.js:156`) — это описано в `docs/TRAVELER-MIGRATION-DIFF.md` как сознательное решение.
- Feature-флаги `TASK_CONFIG` позволяют выключать PowerSpawn/Factory-цепочки без удаления кода — сейчас они выключены.
- Есть мониторинг CPU по подсистемам/ролям + кулдауны сканов (башни — ремонт раз в 15 тиков, атака/лечение — каждый тик, defense-кэш — раз в 25 тиков).

**Соответствие цели:** архитектура соответствует цели «дешёвый, предсказуемый ROI-ориентированный робот на 20 CPU без платного CPU». Проблемы не в архитектуре, а в (а) стоимости построения `roomState` каждый тик, (б) мелких логических дефектах Task System/спавна, (в) хардкоде состояния в коде, (г) отсутствии реакции на bucket.

# 2. Проблемы (только найденное в коде)

### 2.1 Task System / Worker

1. **Worker простаивает по одному типу задач за тик.** `worker.runner.js:17-22`: если очередь пуста — `taskIndex +1` и `return`. Из 11 категорий 4 сейчас всегда пусты (`fillPowerSpawnPower/Energy`, `fillFactoryEnergy`, `collectFactoryBattery` → `TASK_CONFIG=false`), плюс часто пусты `repair/build/upgrade`. Итого воркер теряет по 1 тику на каждый пустой тип при каждом проходе цепочки — это прямые потери логистики основных «курьеров» без выигрыша по CPU.
2. **Комната задачи берётся из `creep.room.name`, а не из `homeRoom`.** `worker.runner.js:11` + `61-62`: `completeTask(roomName = creep.room.name, ...)`. Если воркер физически не в своей комнате (а `room.manager.js:308-318` и `261-265` специально включают «гостящих» крипов в `roomState` другой комнаты), завершение/удаление задачи ищет её в чужой очереди → `completeTask` не находит → воркер логирует ошибку, но запись в исходной очереди остаётся с `reservedBy` живого крипа. Так как `getNextTask` (`task.manager.js:85`) пропускает зарезервированное, а генераторы (`isDuplicate*`) считают такую запись существующей, потребность становится «мёртвой» до смерти крипа.
3. **Резервация до выполнения и «всегда успешный» withdraw.** `energySource.js:24-49` возвращает `true` всегда, если в storage есть энергия, не проверяя результат `creep.withdraw`. В сочетании с резервацией до первого действия (`worker.runner.js:24-38`) это означает: крип считается «прогрессирующим» даже когда действие не прошло. Для нормально работающего крипа безвредно, для спавнящегося — см. п. 4.
4. **Спавнящиеся крипы не пропускаются.** `room.manager.js:48-63` не проверяет `creep.spawning` (в проекте `creep.spawning` вообще не используется, кроме Spawn/Traveler). Воркер в процессе спавна резервирует задачу и держит её все тики спавна (для `worker` это тело 2500 энергии ≈ десятки тиков) — задача блокируется для других воркеров, CPU тратится на роль.
5. **Идентичность потребности реализована не так, как зафиксировано в доке.** Док (`§6`) требует `taskType + targetId + resourceType`, в коде часть функций дополнительно сравнивает `sourceId` (`task.generators.js:24-30, 99-105, 192-198, 245-251, 341-347, 402-408`). Плюс 11 почти идентичных `isDuplicate*`-функций — дублирование и риск разной трактовки одной и той же потребности.
6. **Дедуп — O(цели × очередь).** `task.generators.js:55-72` и аналоги: для каждой цели (60 расширений/башен) делается `some()` по очереди. При 60 целях это ~3600 сравнений на комнату за тик.

### 2.2 CPU / Room Manager

7. **Полное разыменование структур комнаты каждый тик.** `room.manager.js:196-222`: `Game.getObjectById` для всех spawn/tower/link/lab/extension/**road/wall/rampart**/source/storage/terminal/factory/powerSpawn/observer/extractor/nuker, затем `concat` + `filter(s => s.hits < s.hitsMax)` (`249-251`). В развитой комнате это сотни объектов (дороги/стены/валы) и сотни `getObjectById` на комнату за тик. Это главный подозреваемый на CPU, причём большая часть данных нужна не каждый тик.
8. **Скан стен/валов для detectAttack каждый тик.** `room.manager.js:65-86`: `reduce` по всем walls+ramparts + запись `Memory.rooms[roomName].lastWallHits` каждый тик. При этом `detectAttack` вызывается только если у комнаты есть башни (`88-90` ранний return) — значит `lastWallHits`/`underAttack` в комнатах без башен не обновляются вообще (мёртвый флаг, а после постройки башни первый тик даст ложную тревогу).
9. **Роль-CPU мониторинг стоит 2 × `Game.cpu.getUsed()` на каждого крипа каждого тика.** `room.manager.js:53` + `cpuMonitor.js:32-41`, плюс запись `Memory.cpuStats` каждый тик (`cpuMonitor.js:47-56`) и `console.log` каждые 10 тиков (`57-79`) — в Screeps консольный вывод сам по себе стоит CPU, а выводится 7+ строк.
10. **Нет реакции на bucket.** `Game.cpu.bucket` читается только для логирования (`cpuMonitor.js:45,61`); `CPU.BUCKET_CRITICAL` нигде не влияет на поведение. При истощении bucket ничего не отключается.
11. **`observer.manager.js:7` — `Object.values(Game.structures)` каждый тик** по всем структурам всех видимых комнат ради одного observer’а. При этом наблюдение чередует две комнаты по `Game.time % 2` (`14`), а результаты нигде не сохраняются (косвенно помогают defense, давая видимость ремоут-комнат через тик).
12. **Синхронизированные пики сканов.** `TOWER.REPAIR_INTERVAL` (`room.manager.js:107`), defense-кэш `Game.time % 25 === 0` (`defense.manager.js:52`) — все комнаты сканируют в один и тот же тик, вместо разнесения по тикам.
13. **`role.builder.js:22` и `task.generators.js:490`** перебирают `Game.constructionSites` целиком (глобально) и фильтруют по комнате — по крипу и по комнате за тик соответственно.

### 2.3 Traveler (влияние на CPU и скрытые дефекты)

14. **`hostileRooms` фактически не работает.** `traveler.js:33-35`: `this.memory = _.defaultsDeep(_.get(Memory, gOpts.hostileLocation, {}), { hostileRooms: {} })`. `Memory.empire` в проекте никто не создаёт (grep: упоминается только в доке и в самом Traveler), поэтому `_.get` вернёт временный `{}` — запись `this.memory.hostileRooms[...]` в `travelTo` (`171-175`) уходит в мусорный объект и обнуляется каждый тик. Итог: обход враждебных комнат не работает молча (не падает).
15. **Накопительный `_travel.cpu` → лог-спам.** `traveler.js:249-258`: `travelData.cpu` суммируется за всю жизнь крипа и не сбрасывается; после превышения `reportThreshold: 50` каждый последующий пересчёт пути печатает «TRAVELER: heavy cpu use…» (у долгоживущих крипов — постоянно). Плюс `_travel` (включая `cpu`, `count`, `prev`) хранится в `creep.memory` — это постоянный Memory-налог.
16. **Стоимость самого Traveler’а в целом приемлема:** путь кэшируется в `creep.memory._travel` и пересчитывается только при смене цели/застревании; CostMatrix’ы (`getStructureMatrix`) кэшируются на тик на комнату (`293-311`), креповая матрица строится только когда `ignoreCreeps` отключается после 3 тиков застревания (`227-229`). Но каждый репат — это полный `PathFinder.search` (`maxOps: 20000`) + `Game.map.findRoute` при линейной дистанции > 2 (`108-119`), то есть локальные всплески CPU при смене цели у нескольких крипов в одном тике (особенно у ролей, выбирающих «ближайшую» цель: `role.repairer`, `role.builder`, `role.towerSupplier`, `remote.hauler`). Удалённые роли (E35S37↔E35S38/E36S37 — расстояние 1) `findRoute` не вызывают вовсе.

### 2.4 Spawn / роли

17. **Квоты глобальные, гейтится только `mineralMiner`** (`spawn.manager.js:52-57`). Следствия: `labWorker` спавнится в комнатах без конфигов лаб и простаивает, печатая `creep.say("❌ нет конфига")` каждый тик (`lab.worker.js:117-119`); `linkWorker` спавнится там, где нет `Memory.rooms[*].links` и сразу выходит (`role.linkWorker.js:15-18`); `attacker` не спавнится только в E35S37 (`spawn.manager.js:45`), значит в каждой другой своей комнате держится боевой крип 2000 энергии, который в мирное время едет на точку сбора в E35S37 (`defense.attacker.js:22-24, 115-127`) — это и энергия, и межкомнатный pathfinding.
18. **`miner` требует `Memory.rooms[*].minerSpots`, который нигде в коде не создаётся** (только чтение — `creep.factory.js:35`). Где не настроено — голубая печать возвращает `null`, `creep.factory.run` → `ERR_INVALID_ARGS` (`174-185`), и попытка повторяется каждый тик (не фатально, но вечно и без диагностики), а майнеров в комнате нет.
19. **Нет масштабирования тела по доступной энергии** — тело фиксированное (`constants.js:139-154`), `worker` = 2500 энергии; при 20 CPU-бюджете и умеренной экономике это медленный старт ролей, а не ошибка.
20. **`countRole` считает «гостей» другой комнаты** (`spawn.manager.js:9-34` работает по `roomState.creeps`, куда `room.manager.js:308-318` добавляет крипов, физически находящихся в комнате) — счётчики роли в комнате-хозяине завышаются на число визитёров → недоспавн.

### 2.5 Надёжность

21. **Нет изоляции по комнатам.** `room.manager.js:330-368`: `for (const roomState of roomStates) this.runRoom(roomState)`; внутри `runRoom` try/catch есть только у link-логики (`164-172`). Исключение в spawnManager/labManager/generators/towers/factory/powerSpawn прерывает цикл — все последующие комнаты в этом тике остаются без логики (ловится только в `empire.js:52-57` для всего Room Manager’а).
22. **Тайминговый баг кэшей «по количеству крипов».** `remote.manager.js:47-66` и `defense.manager.js:111-122` инвалидируют кэш по `Object.keys(Game.creeps).length`. Если в одном тике умер один крип и родился другой, длина не меняется → список ролей устарел до 50 тиков: новые крипы роли не запускаются, мёртвые просто отфильтровываются.
23. **Двойной механизм распределения ремоут-целей.** `remote.manager.js:17-32` (первая свободная комната) и `remote.hauler.js:30-36` (хэш имени) — второе срабатывает, когда менеджер не смог назначить (например, >2 хайлеров), и грузит уже занятую комнату.
24. **Хардкод состояния игры в коде** (не падает, но ломается молча): `remote.hauler.js:20-27` (ID линков, `HOME_ROOM`), `remote.manager.js:15`, `defense.manager.js:12-15` (два одинаковых списка комнат), `observer.manager.js:3`, `defense.attacker.js:22-24` (точка сбора), `spawn.manager.js:42-45`, `role.harvester`-оверрайды в `constants.js:126-129`. ### 2.6 Экономика / рынок

28. **Комнаты без storage не получают энергии.** `task.generators.js:49-51` (и все остальные генераторы) требуют `storage`; при этом дефолтная квота `harvester: 0` (`constants.js:107`), а оверрайды включены только для E35S37/E35S39. Для молодой комнаты (RCL1-3, без storage) это буквально отсутствие кода, который довёзёт энергию до spawn/extension.
29. **Рынок выключен, но оттока ресурсов нет.** `MARKET.SELL_RESOURCES/BUY_RESOURCES` пусты (`constants.js:184-188`), `MIN_SELL_PRICE_RATIO`/`MAX_BUY_PRICE_RATIO` (`196,200`) не используются нигде. При этом `generateFillTerminalResources` (`task.generators.js:350-392`) переносит излишки из storage в терминал до 10k на ресурс — при выключенном рынке они там и копятся. Продукция лаб (реакции идут, `lab.manager.js`) тоже не имеет выхода, кроме storage.
30. **`terminalNetwork.resetExports` пишет `Memory.rooms[*].terminalExports = {}` каждый тик для каждой комнаты** (`terminalNetwork.js:136-142`) — постоянный Memory-churn без пользы в тики без отправок.
31. **`fillTerminalResources` с неочевидным условием**: `if (!TASK_CONFIG.fillTerminalResources && exportTypes.length === 0) return;` (`task.generators.js:360`) — включённая фича игнорирует отсутствие экспортов, выключенная всё равно работает при их наличии. Скорее всего это не то, что задумано.
32. **Мёртвая проводка PowerSpawn/Factory**: `factory.manager.js` вызывает `produce(RESOURCE_BATTERY)` при любой энергии (cooldown-гейт), `powerSpawn.manager.js` вызывает `processPower()` при power+500 энергии, но задачи `fillFactoryEnergy/collectFactoryBattery/fillPowerSpawn*` выключены в `TASK_CONFIG` — структуры никогда не снабжаются, обе подсистемы фактически no-op (вызовы каждый тик на комнату сохранены).
33. **`role.harvester` и тасковые линии дублируют работу**: `role.harvester` игнорирует резерв storage (`energySource.withdrawFromStorage(creep, true)`, `role.harvester.js:19`), заполняет extensions/spawns — то же делает `fillSpawnsExtensions`. Двойной источник правды по одной потребности.

# 3. Возможности оптимизации

- **Гейт по bucket**: при `Game.cpu.bucket < CPU.BUCKET_CRITICAL` пропускать observer/market/terminalNetwork (существующая константа, ~3 строки в `empire.js`).

- **Разнести периодические сканы по тикам** (индекс комнаты как offset) — убрать синхронные спайки.
- **Табличные сет-ы дедупликации задач** — один проход для построения `Set(ключ потребности)` вместо `some()` на каждую цель.
- **Traveler**: не пересчитывать путь на каждую смену «ближайшей» цели (кэшировать выбранную цель в памяти крипа для `role.repairer/builder/towerSupplier`) и сбросить накопительный `_travel.cpu`/поднять `reportThreshold`, чтобы убрать лог-спам.

- Убрать «1 тип за тик» в `worker.runner` — курьеры начнут работать каждый тик (это же и экономика).

### Defense

- Единая трактовка угрозы (список hostiles из defense-кэша → в `runTowerLogic`, без повторного `room.find`).
- Использовать `Memory.attackAlert.time` для истечения тревоги.

- Для атакующего: учесть, что при отсутствии угроз он стоит в другой комнате — либо держать его в своей комнате, либо уменьшить квоту/тело.
