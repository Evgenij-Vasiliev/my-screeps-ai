## 2. Почему расход был таким: механизм

**Интент стоит 0.2 CPU и входит в `Game.cpu.getUsed()`** — подтверждено исходником драйвера
([`driver lib/runtime/runtime.js:60,68-69,202-203,271`](https://github.com/screeps/driver/blob/master/lib/runtime/runtime.js)):
`intentCpu = 0.2`, начисление один раз за пару «объект + имя интента» в тике, `getUsedCpu = wall + intents.cpu`,
`usedTime = wall + intents.cpu`. Бесплатны только `say` и `pull`.

Отсюда цена «работ» империи (состав — `node scripts/world.facts.js shard3`, 5 комнат RCL8, 16 башен,
755 дорог, 162 стены, 26 валов, 18 линков из них 13 в `senders`, 272 extension, 25–29 крипов):

| Работа | Интентов | CPU только на интенты |
|---|---|---|
| Ремонт башен (все башни, раз в 15 тиков) | 16 | **3.2 CPU** в этом тике |
| Движение + работа крипов | ≤2 на крипа | до 5.0 CPU/тик |
| Линки-отправители | до 13 | до 2.6 CPU/тик |
| Фабрики / PowerSpawn | до 5 + 5 | до 1.0 + 1.0 CPU/тик |

Второй источник — **постоянный JS-налог**: у империи без изменений кода расход «плавал» от 3.29 до 6.26 CPU/тик,
а разброс окон отчёта — от 2.800 до 6.014 CPU/тик. Причина — фазовые пачки, привязанные к `Game.time % N`:

| Период | Что происходит | Где |
|---|---|---|
| **15** | ремонт: все 16 башен империи в ОДИН тик, плюс резолв стен и повреждённых | `constants.js:30`, `room.manager.js`, `role.tower.js` |
| **10** | проход рынка + отчёт монитора | `constants.js:177,183` |
| **20** + сдвиг | перестройка кэша сканера | `scanner.js:106-125` |
| **100** | детектор атаки (резолв всех стен) | `constants.js:34` |

`НОК(10,15) = 30` — на каждом 30-м тике пачки сходились. Это и читалось как «кардиограмма».

### 3.2. Генератор заливки spawn/extension — две правки (на шарде)

`task.generators.js`, функция `generateFillSpawnsExtensions`. Причина: генератор обходил **все 285
spawn/extension империи каждый тик**, чтобы найти те, где есть свободное место. Живая проверка:
во всех 5 комнатах `energyAvailable == energyCapacityAvailable` (12600/12600, 10000/10000, 11600/11600,
10600/10600, 12600/12600), `needy = 0` — обход не находил ни одного кандидата.

Что изменено (поведение не меняется):

1. **Отсев**: `if (room.energyAvailable === room.energyCapacityAvailable) return;` — суммы по всем
   spawn+extension комнаты считает движок (`@types/screeps:4321-4328`). Равенство означает «полны все».
2. Убран промежуточный массив `spawns.concat(extensions)` — один проход по двум спискам.
3. Обход обрывается, когда исчерпан потолок постановки (`addTask` вернул `false`,
   `task.manager.js:253-255`) — раньше ключи дублей строились и после потолка.
4. Свойство `store` читается **один раз** вместо трёх, `storage.id` — раз на комнату:
   в рантайме Screeps доступ к свойству игрового объекта — вызов функции (в драйвере свойства
   `customObjectPrototypes` переопределяются через `eval`). Замер в консоли: три чтения 0.0306 CPU
   против одного 0.0221 на том же проходе (отношение **1.39**).

**Замер до/после** (`gen.fillSpawnsExtensions`, CPU за один тик, 92 окна в каждом прогоне):

| | До | После |
|---|---|---|
| минимум | 0.5894 | **0.0055** |
| 25-й процентиль | 0.8282 | **0.0172** |
| медиана | 0.9518 | 0.8059 |
| тиков «почти ноль» (< 0.01) | **0 из 92** | **18 из 92** |

Наблюдение 30 минут (60 проб, `Memory.cpuStats` через API): `taskManager` медиана **1.0 → 0.4297**,
средний расход **4.797 → 3.932 CPU/тик**.

Тест: `tests/fill.spawns.test.js` (12 проверок), в том числе «при полной комнате `getFreeCapacity`
не вызывается ни разу» и «`store` прочитан ровно по разу на объект».

### 3.3. Башни: фазы по комнатам и политика ремонта (ждёт выгрузки)

Три правки по решению человека.

**(1) Стены исключены из ремонта.** `constructedWall` в Screeps **не распадается вовсе**: движок
`src/processor/intents/constructedWalls/tick.js` не трогает `hits` — только выставляет `hitsMax`
по уровню контроллера и удаляет стену по таймеру `decayTime`, который ставится стенам в ЧУЖОЙ комнате.
Ремонт стен был фиктивной статьёй расхода, а порог `Memory.rooms[r].wallThreshold` бессмысленно рос
на 1000 каждый тик ремонта (стены выше порога всегда). Логика порога удалена; константы
`TOWER.WALL_THRESHOLD_*` помечены как неиспользуемые.

**(2) Одно действие на комнату за тик ремонта, ближайшей башней.** Было 16 интентов каждые 15 тиков
(1.07 действия/тик), стало 5 действий/15 тиков (0.33/тик). Достаточность проверена числами распада:
валы 26 × 3 + дороги 755 × 0.1 = **154 хита/тик**, одно действие башни даёт до **800 хитов**
(`TOWER_POWER_REPAIR`), то есть 267 хитов/тик — с запасом. Ближайшая башня выбрана потому, что у
`repair` есть падение по дальности (`TOWER_OPTIMAL_RANGE 5`, `TOWER_FALLOFF_RANGE 20`).

**(3) Цель — по ДОЛЕ потерянных хитов** `(hitsMax - hits) / hitsMax`, а не по абсолютному дефициту:
`hitsMax` вала на RCL8 — 300 000 000 (`RAMPART_HITS_MAX[8]`), поэтому по абсолютному дефициту вал
выигрывал бы у любой дороги всегда. Цель берётся только если дефицит ≥ одного действия
(`TOWER.REPAIR_POWER = 800`), иначе 10 энергии ушли бы в 1 хит из-за обрезки по `hitsMax`.

**(4) Фаза ремонта по комнатам**: `(Game.time + фаза) % TOWER.REPAIR_INTERVAL === 0`, фаза — хэш имени
комнаты (тот же, что уже разносит перестройку кэша сканера, `scanner.js rebuildStagger`).
Фазы комнат: E35S37 = 2, E35S39 = 4, E37S37 = 1, E37S38 = 2, E36S38 = 10 — **в худшем тике ремонтируют
2 комнаты из 5** (было 5 из 5).

Числа для решения (движок, `@screeps/common lib/constants.js` и `engine src/processor/intents/`):

| Что | Распад / стоимость | Источник |
|---|---|---|
| Стена | **не распадается** | `constructedWalls/tick.js` |
| Вал | 300 хитов за 100 тиков (3/тик), при 0 — удаляется | `RAMPART_DECAY_AMOUNT: 300`, `RAMPART_DECAY_TIME: 100` |
| Дорога | 100 хитов за 1000 тиков (0.1/тик), на болоте ×5, поверх стены ×150 | `ROAD_DECAY_AMOUNT: 100`, `ROAD_DECAY_TIME: 1000` |
| Ремонт башней | 10 энергии → до 800 хитов | `TOWER_ENERGY_COST: 10`, `TOWER_POWER_REPAIR: 800` |

Тест: `tests/tower.attack.test.js` — 18 проверок, включая «стены не резолвятся», «валы резолвятся ровно
один раз», «бьёт только ближайшая башня», «цель — повреждённая дорога, а не почти целый вал»,
«почти целые цели не ремонтируются», «в любом окне 15 тиков ровно один тик ремонта».

## 5. Побочные факты, найденные по ходу

1. **Скачок после рестарта VM.** Сразу после выгрузки кода окно `Memory.cpuStats` считает 14.6–18.3 CPU/тик
   (замеры: `t+0: average 18.30, count 1`; `t+60 с: average 5.11, count 11`) — это холодный старт
   (загрузка 31 модуля, построение кэшей). Пик не связан с логикой бота и проходит за несколько минут.
2. **Консольные замеры не загрязняют измеряемый CPU бота** — проверено экспериментом
   (`scripts/console.budget.test.js`): 5 тяжёлых команд (≈18.5 CPU) внутри одного окна не подняли его сумму.
   Это подтверждает прежнюю заметку проекта `loadShed.js:250-252`.
3. **Длительность тика шарда гуляет** — замерено 3.03, 3.78, ≈6.6 и ≈66 с/тик в разные моменты
   (`GET /api/game/time`). На лимит CPU это не влияет, но любые выводы по wall-clock нужно пересчитывать
   в тики.
4. **`average` монитора не включает финальную сериализацию `Memory`** (она идёт после `game.run`,
   внутри `usedTime` драйвера) — сервер списывает чуть больше, чем показывает монитор.
5. **Мёртвые ключи в `Memory.rooms[*]`.** `wallThreshold` удалён 30.09.2026 через консоль
   (`for(const r in Memory.rooms){delete Memory.rooms[r].wallThreshold}`): был в 5 комнатах из 7,
   130 байт; секция `rooms` 14906 → 14781 байт, бот после удаления тикает (`count` 80 → 90).
   Проверка ключей на ссылки в коде (`grep` по `*.js`) показала, что **под `Memory.rooms` остаётся
   ещё 10 066 байт мёртвых ключей** (68 % секции `rooms`): `diagnostics` 2050, `labs3` 1820,
   `labs2` 1816, `towers` 492, `boostConfig` 430, `defenseCache` 420, `sources` 335,
   `terminalIncoming` 224, `earlySpawnThresholds` 203, `mineralId` 200, `boostLab` 195,
   `taskIdSeed`-подобные `taskIdCounter` 104, `lastAttackTick` 135, `minWallHits` 120,
   `hasSites` 90, `needsRepair` 102, `lastWallHits` 134, `towerAttackCheck` 145,
   `towerAttackMode` 125, `economyMode` 123, `terminalExports` 110, `labWorkerIndex` 100,
   `energyTargets` 100, `_lastStorageEnergy` 138, `factoryProducing` 129, `terminalNeeds` 151,
   `taskIndex` 75, `minWallHits` 120. **Живые ключи: `links`, `labs`, `minerSpots`, `tasks`,
   `underAttack`.** Удаление — по отдельной команде человека.

## 8. Что не сделано / открытые вопросы

* **≈1.0 CPU внутри прежнего пика `towers`** не разложен по частям (3.2 CPU объяснялись 16 интентами,
  остаток — резолвом стен и повреждённых; после правки этот блок исчез целиком, но отдельного замера
  «до» по частям не делалось).
* **Цена каждого генератора задач после правки** не перемерялась (ожидается ≈0 у `fillSpawnsExtensions`
  в «полном» состоянии).
* **Эффект от одиночного чтения `store`** не выделен замером: `taskManager` после первой правки 0.4297,
  после второй 0.4438 — разница в пределах изменения состояния мира.
* **Влияние длительности тика шарда** на измеряемый CPU: корреляции не найдено, гипотеза не проверена.
* **Куда сервер списывает CPU консольной команды** (не в тик бота — проверено) — не проверено.
