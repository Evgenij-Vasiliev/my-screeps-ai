## 1. Главный вывод: `468.46` — это не CPU за тик

`traveler.js` (до правки, строки 247–258) считал стоимость пафайндинга **накопительно за всю жизнь крипа** и не сбрасывал счётчик:

```js
travelData.cpu += Game.cpu.getUsed() - cpu;   // копится и НЕ обнуляется
travelData.count++;
if (travelData.cpu > gOpts.reportThreshold) { // reportThreshold = 50
  console.log(`TRAVELER: heavy cpu use: ... cpu: ${travelData.cpu} ...`);
}
```

`travelData` лежит в `creep.memory._travel` и не сбрасывается нигде (проверено grep: `_travel.cpu`/`count` используются только внутри `traveler.js`).
Отсюда:

- как только крип за жизнь «наездил» на пафайндинг больше 50 CPU, сообщение печатается на **каждом** следующем пересчёте пути — это и есть наблюдаемый спам;
- `468.46` = суммарный CPU всех `PathFinder.search` за жизнь крипа (≤ 1500 тиков), т.е. **≈ 0.31 CPU/тик** в среднем. Это уже тяжело для курьера, но не «468 за один тик».

Это ровно дефект **№15** из `docs/PROJECT_AUDIT_AND_ROADMAP.md` и закрытый этим отчётом пункт задачи №9 («Traveler: `hostileRooms` + лог-спам»).

## 2. Почему нагрузка возникает именно у `harvester`

Логика роли простая (`role.harvester.js`), но она — **курьер с батареей 50 энергии**, а вся стоимость заключается в пафайндинге Traveler.

### 2.1 Малая батарея → много рейсов

- Тело: `constants.js:137` → `harvester: { work: 1, carry: 1, move: 1 }` = 50 энергии за рейс.
- Цикл роли: `storage → (спавн | расширение) → storage`.
- Та же потребность уже закрывается Task System: `task.generators.generateFillSpawnsExtensions` + `worker` с телом `carry: 10` (500 энергии) — в 10 раз меньшим числом рейсов.

Это дефект **№33** аудита: `role.harvester` и `fillSpawnsExtensions` дублируют одну работу.

### 2.2 Смена цели = полный пересчёт пути

`traveler.js:235-242`: путь хранится по получателю и удаляется при любой смене цели:

```js
if (!travelData.dest || travelData.dest.x !== destPos.x || travelData.dest.y !== destPos.y || travelData.dest.roomName !== destPos.roomName) {
  delete travelData.path;   // далее — полный PathFinder.search, maxOps: 20000
}
```

`role.harvester.js:71-77` сбрасывает `targetId`, как только расширение заполнено. Поэтому каждый рейс — это два **новых** пути (в storage и в следующее расширение), каждый — полный `PathFinder.search` с `maxOps: 20000` (`traveler.js:27`).

Итог: маленькая батарея → максимум рейсов → максимум полных пересчётов пути.

### 2.3 Эскалация Traveler при застревании (дорогая creep-матрица)

`traveler.js:214-229`: после 3 тиков без сдвига Traveler ставит `options.ignoreCreeps = false` и пересчитывает путь по creep-матрице (`getCreepMatrix` → `room.find(FIND_CREEPS)` + клон структурной матрицы, `traveler.js:335-350`).

Маленький харвестер едет в самые «плотные» точки (storage и ближние расширения), где одновременно работают большие воркеры, делающие ту же работу. Если цель окружена крипами, поиск может не сойтись (`ret.incomplete`) → пустой `path` → пересчёт **каждый тик** дорогой creep-матрицей.

> **Замером НЕ подтвердилось** (раздел 4.1): у всех пяти харвестеров `stuck = 0`, признаков застревания нет. Гипотеза 2.3 отброшена.

### 2.4 ГЛАВНАЯ ПРИЧИНА (подтверждена замером): матрица комнаты перестраивается на КАЖДЫЙ вызов `travelTo`

`traveler.js:390-414`. Кэш матриц рассчитан «на тик»:

```js
refreshMatrices() {                      // traveler.js:293-299
  if (Game.time !== this.currentTick) {
    this.currentTick = Game.time;
    this.structureMatrixCache = {};      // сброс на новый тик
    this.creepMatrixCache = {};
  }
}
```

Чтобы кэш работал, экземпляр Traveler должен пересоздаваться **один раз за тик** — это и проверяет `global.travelerTick`:

```js
Creep.prototype.travelTo = function (destination, options) {
  if (global.traveler && global.travelerTick !== Game.time) {
    global.traveler = new Traveler();    // пересоздали instance...
  }                                      // ...но travelerTick НЕ обновили
  return global.traveler.travelTo(this, destination, options);
};
```

`global.travelerTick` присваивался только при загрузке модуля (`traveler.js:399`) — то есть равен тику последнего Global Reset. Внутри блока пересоздания его не обновляли, поэтому условие было истинно **всегда** → **каждый** вызов `travelTo` создавал новый экземпляр с пустыми кэшами → CostMatrix комнаты (`room.find(FIND_STRUCTURES)` + `FIND_CONSTRUCTION_SITES` + обход дорог/стен, `traveler.js:312-334`) строилась заново на каждый пересчёт пути вместо одного раза за тик.

Именно это объясняет `avg = 0.10…0.30 CPU` при `pathLen = 1–2` (ход на 1–2 клетки): сам поиск на такое расстояние стоит ~0.01 CPU, а вся стоимость — построение матрицы. Харвестер платит её чаще других ролей, потому что меняет цель на каждой доставке (storage ↔ расширения) и пересчитывает путь каждые 4–12 тиков.

### 2.5 Логика режима энергии расходится с описанием (не про CPU)

`role.harvester.js:19` вызывает `energySource.withdrawFromStorage(creep, true)`. Второй аргумент `true` — это `ignoreReserve`, то есть **аварийный** режим по JSDoc (`energySource.js:17-22`), но он стоит в штатной ветке. Значит, харвестер всегда опустошает storage ниже `STORAGE.ENERGY_MIN`, а ветка «взять из источника» включается только когда пусты **и** storage, **и** терминал.

## 3. Что сделано

Все правки — только в перечисленных файлах; логика снабжения сохранена.

### 3.1 Правка отчёта о стоимости пафайндинга (`traveler.js`, шаг 1)

- `_travel.cpu` / `_travel.count` теперь считают **окно** между отчётами и обнуляются после срабатывания → лог-спам уходит, а `console.log` перестаёт жечь CPU на каждом перепате.
- Добавлен `_travel.cpuTotal` — суммарный CPU пафайндинга за жизнь, только для диагностики (никуда больше не читается).
- В сообщении теперь видно окно, среднее на пересчёт и число пересчётов, например:

```text
TRAVELER: heavy pathing: harvester_E35S39_83031675, cpu: 51.20 за 37 перепчётов (avg 1.384), всего за жизнь: 468.46, pos: [room E35S39 pos 27,17]
```

Семантика `_travel.cpu`/`count` нигде, кроме этого блока, не использовалась, поэтому изменение безопасно.

```diff
-        travelData.cpu += Game.cpu.getUsed() - cpu;
+        const pathCost = Game.cpu.getUsed() - cpu;
+        travelData.cpu += pathCost;
         travelData.count++;
+        travelData.cpuTotal = (travelData.cpuTotal || 0) + pathCost;
         if (travelData.cpu > gOpts.reportThreshold) {
           console.log(
-            `TRAVELER: heavy cpu use: ${creep.name}, cpu: ${_.round(travelData.cpu, 2)}, pos: ${creep.pos}`,
+            `TRAVELER: heavy pathing: ${creep.name}, cpu: ... за ${travelData.count} перепчётов (avg ...), всего за жизнь: ${_.round(travelData.cpuTotal, 2)}, pos: ${creep.pos}`,
           );
+          travelData.cpu = 0;
+          travelData.count = 0;
         }
```

### 3.2 Восстановление кэша матриц (`traveler.js`, шаг 2)

Файл `traveler.js:402-414` — в блок пересоздания экземпляра добавлена строка `global.travelerTick = Game.time;`. Теперь Traveler пересоздаётся один раз за тик, а CostMatrix комнаты строится один раз за тик и переиспользуется всеми вызовами `travelTo`.

```diff
     Creep.prototype.travelTo = function (destination, options) {
       if (global.traveler && global.travelerTick !== Game.time) {
         global.traveler = new Traveler();
+        // без этой строки travelerTick оставался тиком загрузки модуля,
+        // условие было истинно всегда, и матрица комнаты перестраивалась
+        // на КАЖДЫЙ пересчёт пути вместо одного раза за тик.
+        global.travelerTick = Game.time;
       }
       return global.traveler.travelTo(this, destination, options);
     };
```

Замерено после публикации: `matrix: 0.003` (матрица берётся из кэша) — но `avg` пересчёта не изменился. Значит доминирует не матрица, а сам нативный вызов поиска (см. 2.6 и 4.4). Правку оставляем: она убирает лишние перестройки матриц в масштабе всего бота.

### 3.3 Дешёвый короткий ход (`role.harvester.js` + `energySource.js`, шаг 3)

Измерено (4.4): цена `PathFinder.search` определяется самим вызовом (0.04–0.11 CPU), а не длиной пути. Поэтому:

- добавлен локальный `moveTo(creep, target)`: на дистанции 1–2 клетки шагает `creep.move(...)` (почти бесплатно), иначе — `creep.travelTo(...)`;
- застревание прямого шага считается в heap (`global._harvesterMove`, без записи в Memory): после 2 тиков без сдвига роль отдаёт управление Traveler;
- все `creep.travelTo(...)` роли заменены на `moveTo(...)`, включая путь к storage/терминалу: `energySource.withdrawFromStorage(creep, true, moveTo)` (в `energySource.js` добавлен необязательный третий параметр `move`, по умолчанию — `travelTo`, поведение остальных ролей не изменено);
- удалена мёртвая ветка терминала в роли: её полностью покрывает `withdrawFromStorage`.

### 3.4 Двухуровневое тело (`constants.js` + `creep.factory.js`, шаг 3)

- `CREEP_BODIES.harvester` = `{ work: 1, carry: 4, move: 3 }` — 400 энергии, батарея 200 вместо 50 → в 4 раза меньше рейсов (и, значит, меньше вызовов поиска пути);
- `CREEP_BODIES.harvesterEmergency` = `{ work: 1, carry: 1, move: 1 }` — 200 энергии, спавнится, когда `spawn.room.energyAvailable < HARVESTER.NORMAL_BODY_ENERGY` (400), то есть когда в спавнах/расширениях энергии нет и поднять комнату больше нечем;
- константа `HARVESTER.NORMAL_BODY_ENERGY = 400` — в `constants.js`.

Проверки после правок: `node --check` всех затронутых файлов, `npx eslint` — exit 0, `npx tsc --noEmit -p jsconfig.json` — exit 0.

### 4.3 Как читать результаты после правки

- `avg` упал, `reps` прежний → подтверждение, что дело было в матрице; дальше по нагрузке смотреть уже пункты Р1/Р3 (число рейсов), а не пафайндинг.
- `avg` остался ~0.1–0.3 → матрица всё ещё строится слишком часто (например, харвестер единственный, кто пересчитывает путь в тике) → переходить к пункту Р7.
- `reps` растёт сильнее прежнего → пересмотра требует логика роли (структура рейсов), а не Traveler.

### 4.4 Замеры стоимости поиска пути (шаги 6–7)

Измерялось из консоли на живом шарде, код не менялся.

**A. Матрица + «пустой» поиск** (крип стоял рядом с хранилищем):

```text
{"room":"E35S37","creep":"harvester_E35S37_83032730","matrix":0.003,"search":0.043,"ops":0,"steps":0,"incomplete":false}
```

→ матрица берётся из кэша (0.003), но даже поиск, которому нечего искать (`ops: 0`), стоит **0.043 CPU**.

**B. Реальный путь** (от харвестера к контроллеру своей комнаты, 25 клеток):

```text
{"room":"E35S37","creep":"harvester_E35S37_83032730","range":25,"search":0.106,"ops":33,"steps":27,"incomplete":false}
```

→ путь в 25 клеток отработал всего за **33 операции**, но стоил **0.106 CPU**. Значит цена определяется не длиной пути и не сложностью комнаты, а **самим фактом вызова** `PathFinder.search` (ориентировочно 0.04–0.11 CPU).

**Вывод:** сокращать надо не стоимость пути, а **количество вызовов поиска** → отсюда правки 3.3 (короткие переброски без `PathFinder`) и 3.4 (в 4 раза меньше рейсов).

**Суммарная нагрузка харвестеров до правок 3.3/3.4** (за 311 тиков после публикации 3.1/3.2):

|---|---|---|---|
| harvester_E35S37_83032730 | 18.3 | 33 | 0.166 |
| harvester_E35S39_83032743 | 26.1 | 41 | 0.337 |
| harvester_E35S39_83033183 | 33.2 | 44 | 0.479 |
| harvester_E36S38_83033371 | 8.1 | 42 | 0.111 |

Итого ≈ 93 CPU на 5 крипов за 311 тиков ≈ **0.30 CPU/тик на всех харвестеров** при общем потреблении бота ≈ 12 CPU/тик (≈ 2.5%). Это реальный масштаб задачи — а 468 CPU в логе были накопительной суммой за всю жизнь крипа.

### 5.1 Аварийное минимальное тело (выполнено в 3.4)

Реализовано без отдельной роли — ветвлением по доступной энергии внутри блюпринта `harvester` в `creep.factory.js`:

```js
harvester: spawn => {
  const body =
    spawn.room.energyAvailable >= HARVESTER.NORMAL_BODY_ENERGY   // 400
      ? CREEP_BODIES.harvester          // {work:1, carry:4, move:3}
      : CREEP_BODIES.harvesterEmergency // {work:1, carry:1, move:1} = 200
  ...
}
```

`spawn.room.energyAvailable` — это ровно та энергия, которой может распорядиться спавн (спавны + расширения), поэтому проверка совпадает с определением аварийной ситуации: «в спавнах и расширениях энергии нет» → спавнится минимальное тело, и роль продолжает работать.

- Общий перевод `roomState` на ленивое разыменование (баг №7, крупнейший подозреваемый по CPU на уровне комнаты) в этот отчёт не входит.
