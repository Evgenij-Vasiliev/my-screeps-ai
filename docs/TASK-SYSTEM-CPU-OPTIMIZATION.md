## 1. Как измерялось

Второго мониторинга CPU не создавалось. Использованы те же два механизма, что в ТЗ №0/№1:

| Что | Как |
| --- | --- |
| Блок `taskManager` целиком | существующий бакет `cpuMonitor.trackRole("taskManager")` (`room.manager.js`) |
| Выполнение Task System (`worker`) | существующий бакет роли `worker` (`runCreepLogic` → `worker.runner`) |
| Вклад каждого из 11 генераторов | под-бакеты `taskGen:<категория>` там же, `taskGen`-вызовы стоят **внутри** бакета `taskManager`, порядок вызовов не изменён |
| Вклад `worker` по фазам | под-бакеты `workerPick` / `workerExec` / `workerFinish` в `worker.runner` (внутри бакета `worker`) |
| Адресные счётчики (вызовы, ранние выходы, очередь, резервации) | плоские числа в `global._tsCounters`, снимок раз в `CPU.PROFILE_REPORT_INTERVAL` (100 тиков) в `Memory.cpuStats.ts` — выгрузка `screeps-api`, `memory.get` |
| Функциональный контроль «логистика не сломалась» | снимок раз в 20 тиков: энергия в спавнах/расширениях и башнях (`avg`/`min`), `ticksToDowngrade` |
| Цена отдельных примитивов | консольный A/B на живом шарде (`/tmp/ts/bench*.js`) — один и тот же набор целей, тот же тик |
| Очереди до/после | `Memory.rooms[*].tasks` в снимке счётчиков: длина, зарезервированные, мёртвые резервации, дубли по ключу `taskType|targetId|resourceType` |

Формулы те же, что в ТЗ №0: `avg = sum / samples`; доля = `avg_блока / avg_roomManager`;
цена вызова генератора = `sum` под-бакета ÷ (5 комнат × число инструментированных тиков);
цена действия = `sum / count`.

Инструментализация включается/выключается **одним** флагом `CPU.PROFILE_ENABLED` (`constants.js`) и
после контрольного окна снята полностью (раздел 4.4).

Честные границы метода:

1. Под-бакеты — это **вложенные** `Game.cpu.getUsed()` замеры. Их цену видно по «пустым» генераторам:
   вызов, который ничего не делает, но измеряется (`trackRole` + счётчик), стоит 0.6–0.9 мкс, то есть
   пара `getUsed()` ≈ 0.5–0.8 мкс. На 55 вызовов генераторов и ~1100 счётчиков за тик это
   **≈0.05–0.10 мс/тик** к `taskManager` (проверяется разностью инструментированного и чистого окон,
   §4.4). Поэтому «до/после» сравниваются **в одинаково инструментированных окнах**, а итоговый
   критерий приёмки — на окне **без** инструментализации.
2. Консольные A/B-числа (раздел 2.4) в абсолюте не сопоставимы с игровыми: код в консоли
   интерпретируется без JIT-прогрева, поэтому μs в консоли ≈ в 10² раз больше игровых. Значимо там
   только **отношение** вариантов в одном и том же запуске; итоговый эффект берётся из игровых окон.
3. Окно профиля `Memory.cpuStats.profile` накопительное с `startTick`, а окно счётчиков живёт в heap
   и обнуляется при каждом деплое (Global Reset). Поэтому «до» для CPU берётся разностью двух
   снимков профиля, а «до» для счётчиков — последним снимком перед деплоем правки.

### 4.4 Инструментализация снята (решение и обоснование)

Измерительный слой **снят полностью**, не оставлен «опциональным». Обоснование:

1. тот же подход применён в двух предыдущих задачах (`miner`, `remoteManager`) — обёртки возвращаются
   к оригиналу сразу после окна;

3. метрики CPU системно решаются отдельной задачей 5 роадмапа («дешёвый CPU-мониторинг + гейт по
   `bucket`»), а не остаточным слоем внутри Task System.

### 5.4 Почему цель по `worker`/Task System не достигнута (и что с этим делать)

Цель §5.1 (Task System ≤ 1.20, `worker` ≤ 0.65) исходила из гипотез H3/H4 — что `worker` дорог на
idle-тиках и обходе очередей. Замер это опроверг: idle-тик стоит ≈0.003 мс, весь обход очередей —
3.2 % блока, а 88–91 % `worker` — это **вызов executor'а** (`travelTo` в комнате + `transfer`/`repair`),
то есть полезная работа. Отсюда два следствия:

1. у `worker` нет «пустой» части, которую можно убрать в рамках области ТЗ: чтобы уложиться в 0.65 мс,
   нужно снижать цену/число `travelTo`-вызовов — это `task.executors.js` и Traveler (задача 9 роадмапа,

- **«`getNextTask` отдавать индекс» (P7, третья часть) — отказ.** `tm.findIndexScanned` = 2.2 элемента
  очереди за тик: эффект ниже 0.001 мс/тик, а смена сигнатуры `getNextTask` затронула бы и дедуп
  генераторов, и мок-тесты. Дешевле было убрать бессмысленный `initRoomTasks` на каждый `addTask`.
- **`repairStructures` (670 структур/тик, 0.078 мс/тик) не оптимизирован.** Почти все повреждённые
  структуры — дороги в пределах 1 % от максимума хитов; цикл из 670 проверок порога не создаёт задач.
  Убрать его можно только сменой частоты скана (кэш в heap с TTL), то есть **поведенческим** изменением
  (задача ремонта появится на N тиков позже) — в области правки этого ТЗ нет. Это следующая по величине
  статья `taskManager` после `fillSpawnsExtensions`.
- **Executor'ы и Traveler (`task.executors.js`, `traveler.js`) не тронуты — 88 % блока `worker`.**
  ТЗ явно выводит Traveler за область (задача 9 роадмапа). Именно поэтому цель §5.1 `worker ≤ 0.65`
  недостижима в рамках этого ТЗ: измеренная цена `worker` — это в основном `travelTo` + действие
  (0.18 мс на вызов executor'а), то есть полезная работа. Путь к снижению — ровно то, что делает
  задача 9 (меньше пересчётов пути, `isNearTo` перед action-вызовом, кэш маршрутов), и его следует
  планировать отдельным окном с адресными замерами, как в `docs/REMOTE-CPU-OPTIMIZATION.md`.
- **Вне области (по ТЗ, не трогалось):** ленивый `roomState` (задача 1), квоты и гейты спавна
  (задача 7), `energySource`/`withdrawFromStorage` (задача 3 аудита), гейт по `bucket` (задача 5),
  состояние игры в `Memory` (задача 12).

## 8. Итог

**`taskManager` снижен на 41 % в прямом инструментированном сравнении (0.9824 → 0.51 мс/тик по
difference-in-differences оценке; цель ≤ 0.55 достигнута) за счёт одного генератора
`fillSpawnsExtensions` (165.8 → 58.3 мкс за вызов: чтение состояния целей подешевело, цели с уже
существующей Task отсекаются до чтения, дедуп стал одним проходом), а `worker` вырос на 41 % потому,
что стал выполнять в 3.6 раза больше полезной работы — итог по блоку Task System: **1.85 → 1.75 мс/тик
при пропускной способности логистики ×3.6 и цене 1.29 мс на завершённую задачу вместо 3.27 мс**.

Осталось по роадмапу (не входило в это ТЗ):

- **задача 9 (Traveler + `task.executors.js`)** — единственный путь к цели `worker ≤ 0.65`
  (88–91 % блока): `isNearTo` перед action-вызовом вместо неудачного вызова, меньше пересчётов пути;
- **`repairStructures`** — 670 проверок порога за тик (≈0.06 мс/тик) при 0–1 создаваемой задаче:
  требует кэша порога со TTL (поведенческое решение, отдельным шагом);
- **задачи 1, 4, 5, 7, 11, 12 роадмапа** — не трогались (вне области ТЗ), статусы обновлены в
  `docs/PROJECT_AUDIT_AND_ROADMAP.md`.
