## Шаг 1. Рынок: throttle и кэш ордеров ⭐ максимальный эффект

**Файлы:** `market.manager.js:43, 87, 100, 171, 188`
**Проблема:** `Game.market.getAllOrders()` в цикле `group(4) → terminal(T) → resourceType(R)` каждый тик. Лимит сделок останавливает цикл только после *успешной* сделки — при их отсутствии сканируются все ресурсы всех терминалов.

**Что делать:**
1. `run()` вызывать не каждый тик: `if (Game.time % MARKET_INTERVAL !== 0) return;` (интервал 10–20 тиков, вынести в `constants.js`).
2. Кэш ордеров на тик: `global.marketOrders[Game.time]`, один вызов `getAllOrders({type, resourceType})` на ресурс — вместо повтора для каждого терминала.
3. Сначала считать `surplus`, обращаться к рынку **только** при `surplus > 0` и только для ресурсов из списка избыточных.
4. `getEmpireTerminals()` (`:87`) — кэшировать список комнат с терминалами в `global`, обновлять раз в N тиков.
5. `Math.min(...orders.map(...))` (`:50`, `:107`) заменить на цикл (масштабируемость + риск переполнения стека).

**Приёмка:** замер до/после `marketManager.run()` — снижение в разы; число сделок и их результат не изменились.
**Откат:** убрать throttle (`MARKET_INTERVAL = 1`) — поведение возвращается к прежнему.
**Риск:** низкий (задержка реакции рынка на 10–20 тиков).

## Шаг 2. Дублирование крипов в `roomState` — баг + двойной CPU

**Приёмка:** сумма длин `roomState[*].creeps` = `Object.keys(Game.creeps).length`; двойных интентов по одному крипу нет.
**Откат:** `git revert` (правка локализована в одной функции).
**Риск:** средний — проверить дальнюю добычу (крипы вне дома).

## Шаг 4. Инвалидация кэша структур — функциональный баг

**Файл:** `scanner.js:14-26`, `constants.js` (`CACHE.REFRESH_INTERVAL: 20` объявлен и не используется)
**Проблема:** новые extensions/roads/walls/towers навсегда выпадают из `roomState` → спавн их не заполняет, ремонт не видит, башни не чинят.

**Что делать:**
1. Кэш — в `global.structureCache[roomName]` с полем `updatedAt`.
2. Пересканирование при `Game.time - updatedAt >= CACHE.REFRESH_INTERVAL` **и** по событиям: изменение `controller.level`, завершение стройки (`EVENT_STRUCTURE_BUILT` / исчезновение площадок).
3. В `Memory` оставить только `mineralId`/`extractorId` (нужны после рестарта), остальное — heap.

**Приёмка:** построенный extension появляется в `roomState.extensions` в пределах 20 тиков; ремонт видит новые дороги.
**Откат:** вернуть прежнюю проверку «массивы непусты».
**Риск:** средний — следить за ростом CPU на пересканировании (замер до/после).

## Шаг 5. Статику — из `Memory` в heap

**Файлы:** `scanner.js:38`, `role.tower.js:12-17`, `room.manager.js:76,102,131`
**Проблема:** `structureCache` (массивы id стен/валов/дорог, 7–10 КБ на комнату), `towerState`, `lastWallHits`, `underAttack`, `wallThreshold` сериализуются каждый тик.

**Что делать:**
1. `structureCache`, `towerState`, детектор атаки — в `global`; в `Memory` только значения, обязанные переживать рестарт, и только при изменении.
2. Убрать `Memory.towerState` целиком — флаг уже есть в `Memory.rooms[room].underAttack` (`room.manager.js:102`).
3. Записывать в `Memory` **только при смене значения** (`if (prev !== next)`).

**Приёмка:** `RawMemory.get().length` снижается на ожидаемый объём; поведение башен/детектора не изменилось.
**Откат:** вернуть запись в `Memory` (правки локальны).
**Риск:** средний — heap теряется при рестарте, предусмотреть перестройку в первом тике.

**Файлы:** `role.builder.js:22`, `task.generators.js:485`

3. `generateBuildStructures` — `Set` существующих `targetId` вместо `tasks.some(...)` на каждую площадку.

**Приёмка:** в `role.builder` нет `Object.values(Game.constructionSites)`; выбор цели идентичен прежнему.
**Откат:** `git revert`. **Риск:** низкий.

## Шаг 7. Детектор атаки и башни: реже и без лишних записей

**Файлы:** `room.manager.js:62-83, 104-157`, `role.tower.js`
**Проблема:** каждый тик на комнату — `[].concat(walls).concat(ramparts)` + `reduce` по 200–500 объектам + запись `lastWallHits`; башни пишут `Memory.towerState` на каждую башню.

**Что делать:**
1. Проверку падения hits выполнять раз в `TOWER.HOSTILE_CHECK_INTERVAL` (100) тиков.
2. В остальные тики сигнал атаки — `room.find(FIND_HOSTILE_CREEPS)`: движок кэширует `room.find` в пределах тика, это дешевле JS-обхода списка id.
3. `walls`/`ramparts` в `buildRoomState` резолвить **лениво** — только в «тик ремонта» (`Game.time % TOWER.REPAIR_INTERVAL === 0`).
4. `role.tower`: убрать `Memory.towerState` (см. Шаг 5).

**Приёмка:** обход стен — 1 раз на 100 тиков вместо 100; реакция на атаку не ухудшилась.
**Откат:** вернуть `TOWER.HOSTILE_CHECK_INTERVAL = 1`.
**Риск:** средний — проверить сценарий реального нападения (снижение hits без hostile-крипов).

## Шаг 9. Задачи: убрать копию в памяти крипа и линейные сканы

**Файлы:** `worker.runner.js:41, 66`, `task.manager.js:45-139`, `task.generators.js` (11 × `isDuplicate*`)
**Проблема:** полная копия задачи в `Memory.creeps[*].task` (~5–10 КБ на империю); `getNextTask`/`findIndexByTaskId` — O(n) на каждого воркера и каждую операцию; 11 дублирующих `isDuplicate*` с 4-уровневой цепочкой `Memory` внутри колбэка.

**Что делать (по частям, каждая часть — отдельный коммит):**
1. В памяти крипа — только `taskId` + `taskType`; задача резолвится через heap-индекс.
2. `global.taskIndex` — `Map<taskId, task>` + счётчик свободных на тип, инвалидация по dirty-флагу при изменении `Memory`.
3. `completeTask` — `delete` из `Map` + ленивая компактизация раз в N тиков вместо `splice`.
4. Один хелпер `Set` ключей `type|targetId|sourceId|resourceType` вместо 11 функций.
5. `TASK_TYPE_SET = new Set(TASK_CHAIN)` на уровне модуля; `initRoomTasks` — раз на комнату за тик.
6. Кэшировать «очередь пуста» на тик, чтобы холостые воркеры не сканировали её заново.

**Приёмка:** воркер получает/завершает те же задачи; `Memory.creeps[*].task` отсутствует; число сравнений на тик падает с O(n²) до O(n).
**Откат:** по частям — 1 и 2 независимы от 3–6.
**Риск:** **высокий** (ядро Task System) — делать после Шагов 1–8, под нагрузочным тестом.

### Осознанно не сделано

- **Шаг 10** (`buildRoomState`: ~13 аллокаций массивов на комнату, фильтрация ~250 структур
  на комнату каждый тик, `Object.values(Game.rooms/creeps)`) — **самый крупный оставшийся
  резерв**: подсистемы вместе дают ~0.5–1.6 CPU/тик, а общее среднее ~7.5, то есть ~90 %
  расхода вне подсистем — это логика крипов и сборка `roomState`.
- **Шаг 11** (мелочи ролей: `reusePath`, `visualizePathStyle`, `memory.working` только при
  смене режима, ленивый резолв в `task.executors`).

- **`splice` в `completeTask`** оставлен намеренно: ленивая компактизация оставляет `null`-дыры
  в массиве, который сериализуется в Memory, и сломала бы `getNextTask` на следующем тике.

### Как читать результат

`Memory.cpuStats` пишется раз в 10 тиков и содержит `average`, `bucket`, `creeps` и
`subsystems` — разбивку CPU/тик по подсистемам. Это основной инструмент контроля после
любого следующего изменения.
