# Screeps — Архитектура зрелой империи

## Часть 3. Task System (Система задач)

---

# Главная идея

После перехода от ролей к сервисной архитектуре возникает вопрос:

```text
Кто управляет крипами?
```

Ответ:

```text
Task System
```

Крипы больше не принимают решения самостоятельно.

Они выполняют задачи, созданные другими системами.

---

# Что такое задача

Задача (Task) — это минимальная единица работы.

Например:

```js
{
    type: "transfer",
    from: storage.id,
    to: extension.id,
    amount: 50
}
```

Или:

```js
{
    type: "upgrade",
    target: controller.id
}
```

Или:

```js
{
    type: "repair",
    target: road.id
}
```

---

# Основной принцип

Система создаёт задачу.

Крип выполняет задачу.

Система не управляет крипом напрямую.

---

# Жизненный цикл задачи

Полный путь выглядит так:

```text
System
    ↓
Task Creation
    ↓
Task Queue
    ↓
Scheduler
    ↓
Dispatcher
    ↓
Creep
    ↓
Execution
    ↓
Complete
```

---

# Кто создаёт задачи

Разные сервисы создают разные типы задач.

---

## Логистика

Создаёт:

```text
withdraw
transfer
pickup
dropoff
```

Пример:

```js
{
    type: "transfer",
    resource: RESOURCE_ENERGY,
    from: storage.id,
    to: spawn.id,
    amount: 300
}
```

---

## Строительство

Создаёт:

```text
build
```

Пример:

```js
{
    type: "build",
    target: constructionSite.id
}
```

---

## Ремонт

Создаёт:

```text
repair
```

Пример:

```js
{
    type: "repair",
    target: road.id
}
```

---

## Апгрейд

Создаёт:

```text
upgrade
```

Пример:

```js
{
    type: "upgrade",
    target: controller.id
}
```

---

## Военная система

Создаёт:

```text
attack
heal
dismantle
reserve
claim
```

---

# Очередь задач

После создания задача попадает в очередь.

```text
Task Queue
```

Пример:

```js
[task1, task2, task3, task4];
```

---

# Зачем нужна очередь

Очередь позволяет:

- хранить задачи;
- сортировать задачи;
- распределять задачи;
- отслеживать выполнение.

---

# Проблема приоритетов

Не все задачи одинаково важны.

Например:

```text
Заполнить Spawn
```

важнее чем:

```text
Построить дорогу
```

---

# Приоритеты

Обычно каждой задаче назначается приоритет.

Например:

```js
{
    type: "transfer",
    priority: 100
}
```

---

Пример шкалы:

```text
100 = критично
80  = очень важно
60  = важно
40  = обычная задача
20  = низкий приоритет
```

---

# Scheduler

Scheduler отвечает за выбор задач.

Он решает:

```text
Какая задача должна быть выполнена первой?
```

---

Схема:

```text
Task Queue
      ↓
 Scheduler
      ↓
 Sorted Queue
```

---

# Пример

Имеются задачи:

```text
Строительство дороги
Заполнение Spawn
Ремонт дороги
Апгрейд контроллера
```

После сортировки:

```text
Заполнение Spawn
Апгрейд контроллера
Ремонт дороги
Строительство дороги
```

---

# Dispatcher

Следующий уровень.

Dispatcher отвечает на вопрос:

```text
Кто будет выполнять задачу?
```

---

Схема:

```text
Scheduler
     ↓
Dispatcher
     ↓
Creep
```

---

# Пример

Есть задача:

```js
{
  type: "transfer";
}
```

Есть три перевозчика:

```text
Hauler A
Hauler B
Hauler C
```

Dispatcher выбирает лучшего исполнителя.

---

# Критерии выбора

Обычно учитываются:

```text
Расстояние
Свободность
Размер груза
Оставшаяся жизнь
Загрузка крипа
```

---

# Назначение задачи

После выбора исполнителя:

```js
creep.memory.taskId = task.id;
```

---

Задача становится:

```js
task.assigned = true;
```

---

# Executor

Исполнитель находится внутри крипа.

Он не думает.

Он выполняет.

---

Пример:

```js
switch (task.type) {
  case "transfer":
    runTransfer(task);
    break;

  case "repair":
    runRepair(task);
    break;

  case "build":
    runBuild(task);
    break;
}
```

---

# Завершение задачи

После выполнения:

```js
task.status = "completed";
```

или

```js
delete task;
```

---

# Возможные состояния задачи

```text
CREATED
QUEUED
ASSIGNED
RUNNING
COMPLETED
FAILED
CANCELLED
```

---

# Полезное правило

Задача должна хранить только информацию о работе.

Не информацию о крипе.

Плохо:

```js
{
    type: "transfer",
    creep: "Bob"
}
```

---

Хорошо:

```js
{
    type: "transfer",
    from: storage.id,
    to: spawn.id
}
```

---

# Почему это важно

Если крип умер:

```text
Крип исчез
Задача осталась
```

Система автоматически назначит нового исполнителя.

---

# Система становится устойчивой

В зрелой архитектуре:

```text
Крипы временные
Задачи постоянные
```

Это один из важнейших принципов.

---

# Переход от ролей к задачам

Ролевая модель:

```text
Role Builder
    ↓
Сам ищет стройку
Сам принимает решение
Сам работает
```

Task System:

```text
Build Task
     ↓
Dispatcher
     ↓
Executor
```

Решение принимается системой, а не крипом.

---

# Масштабирование

При росте империи:

```text
10 крипов
100 крипов
1000 крипов
```

количество типов задач почти не меняется.

Это одна из причин высокой масштабируемости Task System.

---

# Полная архитектура

```text
Empire
    ↓
Policy
    ↓
Systems
    ↓
Tasks
    ↓
Scheduler
    ↓
Dispatcher
    ↓
Executors
    ↓
Creeps
```

---

# Главные выводы

1. Задача — минимальная единица работы.

2. Системы создают задачи.

3. Scheduler определяет порядок выполнения.

4. Dispatcher выбирает исполнителя.

5. Executor выполняет задачу.

6. Крипы не принимают стратегических решений.

7. Задачи должны жить независимо от крипов.

8. Чем меньше логики находится в крипе, тем проще масштабировать империю.
