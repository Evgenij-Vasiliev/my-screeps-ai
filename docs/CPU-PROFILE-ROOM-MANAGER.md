## 1. Что именно измеряется

Измерения выполняются **тем же** механизмом `cpuMonitor.trackRole()`, что и весь существующий
мониторинг (второго независимого мониторинга CPU не создано). Добавлены только обёртки вокруг
крупных блоков `room.manager.js` и слой агрегации в `cpuMonitor.js`.

## 2. Как снимается статистика

### 2.1 Механизм и нагрузка

- каждый тик значения `roleCPU` складываются в **heap-окно** (`cpuMonitor.profileWindow`):
  только сложение чисел, **без обращений к `Memory`** и без новых `Game.cpu.getUsed()` вокруг крипов/объектов;
- добавлены всего **2 обёртки `trackRole` на комнату за тик** (`roomState` — один раз на тик, `room:<имя>` —
  по одной на комнату), т.е. рост числа `getUsed()` ≈ `2 + 2 × (число комнат)` на тик;
- раз в **`CPU.PROFILE_REPORT_INTERVAL = 100`** тиков окно переносится в `Memory.cpuStats.profile`
  и печатается **одна** строка сводки (`console.log` один раз на 100 тиков).

### 2.2 Где лежат данные

Данные хранятся в **существующем** механизме `Memory.cpuStats` отдельным подразделом —
существующая структура (`total`/`count`/`average`) не изменена:

```
Memory.cpuStats.profile = {
  startTick: <тик начала сбора>,
  samples:   <сколько тиков накоплено>,
  blocks: { roomManager: { sum, max, count }, roomState: {...}, ... },
  rooms:  { E35S37: { sum, max, count }, ... }
}
```

`sum` — сумма CPU за все накопленные тики, `max` — максимальный CPU за один тик, `count` — сколько тиков
блок реально выполнялся (для ролей/башен может быть меньше `samples`).

### 2.3 Что печатает бот (не чаще 1 раза в 100 тиков)

Шаблон строки (значения подставляются из замеров; ничего не рассчитывается заранее):

```
=== CPU PROFILE (ТЗ №0) | tick <tick> | замеров: <samples> | период: <N> тиков (с <startTick>) ===
roomManager <avg> | roomState <avg> (<доля>% от roomManager)
taskGen <avg> | TaskSystem <avg> | spawn <avg> | lab <avg> | towers <avg> | link <avg> | factory <avg> | powerSpawn <avg>
роли (топ-5): <роль> <avg> | ...
комнаты: <комната> <avg> | ...
```

Дополнительно вручную (когда угодно) из консоли игры:

```js
require("cpuMonitor").reportProfile(); // та же строка сводки
JSON.stringify(Memory.cpuStats.profile); // полный дамп накопленного профиля
```

### 2.4 Как отключить/удалить инструментализацию

- выключить сбор, не удаляя код: `CPU.PROFILE_ENABLED = false` в `constants.js` (сбор и печать прекращаются);
- сбросить только замеры: `delete Memory.cpuStats.profile`;
- сбросить всю статистику вместе с существующей: `delete Memory.cpuStats`;
- полное удаление — удалить в `cpuMonitor.js` секцию «ПРОФИЛИРОВАНИЕ ROOM MANAGER», вызовы
  `accumulateProfile/flushProfile/reportProfile` в `endTick`, два `trackRole` в `room.manager.js:run`
  и `CPU.PROFILE_*` в `constants.js` (`PROFILE_ENABLED`/`PROFILE_REPORT_INTERVAL`), после чего
  `trackRole` можно вернуть к прежнему виду (без `return`).

### 2.5 Как снять данные для этого отчёта (живой шард)

Порядок для оператора:

1. задеплоить проект (текущий `Gruntfile.js`: ветка `test`);
2. дать боту набрать статистику. **Рекомендуемый период измерения: не менее 2–3 суток
   (≈ 20 000–30 000 тиков).** Минимум для устойчивых средних — 10 000 тиков
   (`samples` в `Memory.cpuStats.profile`);
3. один раз выполнить в консоли игры сниппет ниже — он печатает **готовые markdown-таблицы**
   для разделов 3–5 этого файла (`avg CPU/тик` = `sum / samples`, `max` = максимум за один тик):

```js
(() => {
  const p = Memory.cpuStats && Memory.cpuStats.profile;
  if (!p || !p.samples) return "Нет данных: Memory.cpuStats.profile пуст";
  const s = p.samples;
  const avg = e => (e ? e.sum / s : 0);
  const line = (label, e) =>
    "| " +
    label +
    " | " +
    avg(e).toFixed(3) +
    " | " +
    (e ? e.max.toFixed(3) : "-") +
    " | " +
    (e ? e.count : 0) +
    " |";
  const main = [
    ["средний CPU room.manager", "roomManager"],
    ["buildRoomState", "roomState"],
    ["генерация задач (taskManager)", "taskManager"],
    ["выполнение Task System (worker)", "worker"],
    ["tower logic (towers)", "towers"],
    ["link manager", "linkManager"],
    ["factory manager", "factoryManager"],
    ["powerSpawn manager", "powerSpawnManager"],
    ["lab manager", "labManager"],
    ["spawn manager", "spawnManager"],
  ];
  const known = main.map(m => m[1]);
  const rows = main.map(m => line(m[0], p.blocks[m[1]]));
  const roles = Object.keys(p.blocks)
    .filter(
      n =>
        known.indexOf(n) === -1 &&
        n.indexOf("Manager") === -1 &&
        n !== "terminalNetwork",
    )
    .sort((a, b) => p.blocks[b].sum - p.blocks[a].sum);
  const rooms = Object.keys(p.rooms).sort(
    (a, b) => p.rooms[b].sum - p.rooms[a].sum,
  );
  let out =
    "период: с тика " +
    p.startTick +
    " по " +
    Game.time +
    " (" +
    (Game.time - p.startTick + 1) +
    " тиков), замеров: " +
    s +
    ", крипов: " +
    Object.keys(Game.creeps).length +
    "\n\n" +
    "| Блок | avg CPU/тик | max CPU/тик | тиков активности |\n|---|---|---|---|\n" +
    rows.join("\n") +
    "\n";
  out +=
    "\n| Роль | avg CPU/тик | max CPU/тик | тиков активности |\n|---|---|---|---|\n" +
    roles.map(n => line(n, p.blocks[n])).join("\n") +
    "\n";
  out +=
    "\n| Комната | avg CPU/тик | max CPU/тик | тиков активности |\n|---|---|---|---|\n" +
    rooms.map(n => line(n, p.rooms[n])).join("\n") +
    "\n";
  const rm = avg(p.blocks.roomManager);
  out +=
    "\nroomState / roomManager = " +
    (rm > 0 ? ((avg(p.blocks.roomState) / rm) * 100).toFixed(1) + "%" : "n/a");
  return out;
})();
```

4. вставить полученные таблицы и период в разделы 4.1–4.7 ниже;
5. доля каждого блока считается как `avg_блока / avg_roomManager` (обе величины — фактические замеры,
   никаких «ожидаемых процентов»);
6. «накладные расходы» `runRoom` (не отнесённые ни к одной подсистеме) считаются как
   `Σ room:* − (taskManager + worker + все роли + towers + linkManager + factoryManager + powerSpawnManager + labManager + spawnManager)`
   — это одновременно стоимость самого измерения (`trackRole` вокруг каждого крипа и каждой подсистемы,
   2 × `Game.cpu.getUsed()` на вызов) и «пустая» работа менеджера между подсистемами.
   Эту величину обязательно указывать в выводах — она входит в CPU `room.manager` и раньше нигде не измерялась.

## 5. Краткий вывод: что фактически является главным потребителем CPU

_Раздел заполняется после сбора данных._ Ниже — заранее зафиксированное правило вывода, чтобы вывод
был механическим и не зависел от ожиданий:

1. **Главный потребитель** — блок с наибольшим `avg CPU/тик` и подтверждённой долей от `roomManager`
   (таблица 4.1).
2. Если первое место занимает `roomState` и его доля ≥ 40 % — вывод: «главный потребитель — построение
   `roomState` (разыменование всех структур + дорог/стен/валов каждый тик)»; это количественно
   подтверждает или опровергает гипотезу из аудита проекта.
3. Если первое место занимают роли/`worker` — вывод: «главный потребитель — ролевая логика /
   выполнение Task System», а `roomState` — второстепенный фактор (привести его фактическую долю).
4. Если заметную долю (> 10–15 %) занимают «накладные расходы `runRoom` + сам замер» — значит
   значительная часть `room.manager` — не полезная работа, а сам `trackRole`
   (2 × `Game.cpu.getUsed()` на каждого крипа и на каждую подсистему). Это измеренная величина,
   и её тоже надо назвать в выводе.
5. Для каждой подсистемы из 4.5 указать факт: «дороже/дешевле 1 % от `roomManager`» — то есть стоит ли
   вообще трогать tower/link/factory/powerSpawn в оптимизациях.

Итоговая строка вывода: _ожидает данных_.
