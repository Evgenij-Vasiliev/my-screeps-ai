## 2. Как снимается статистика

### 2.1 Механизм и нагрузка

- каждый тик значения `roleCPU` складываются в **heap-окно** (`cpuMonitor.profileWindow`):
  только сложение чисел, **без обращений к `Memory`** и без новых `Game.cpu.getUsed()` вокруг крипов/объектов;
- добавлены всего **2 обёртки `trackRole` на комнату за тик** (`roomState` — один раз на тик, `room:<имя>` —
  по одной на комнату), т.е. рост числа `getUsed()` ≈ `2 + 2 × (число комнат)` на тик;
- раз в **`CPU.PROFILE_REPORT_INTERVAL = 100`** тиков окно переносится в `Memory.cpuStats.profile`
  и печатается **одна** строка сводки (`console.log` один раз на 100 тиков).

### 2.2 Где лежат данные

Данные хранятся в **существующем** механизме `Memory.cpuStats` отдельным подразделом —
существующая структура (`total`/`count`/`average`) не изменена:

```
Memory.cpuStats.profile = {
  startTick: <тик начала сбора>,
  samples:   <сколько тиков накоплено>,
  blocks: { roomManager: { sum, max, count }, roomState: {...}, ... },
  rooms:  { E35S37: { sum, max, count }, ... }
}
```

`sum` — сумма CPU за все накопленные тики, `max` — максимальный CPU за один тик, `count` — сколько тиков
блок реально выполнялся (для ролей/башен может быть меньше `samples`).

### 2.3 Что печатает бот (не чаще 1 раза в 100 тиков)

Шаблон строки (значения подставляются из замеров; ничего не рассчитывается заранее):

```
=== CPU PROFILE (ТЗ №0) | tick <tick> | замеров: <samples> | период: <N> тиков (с <startTick>) ===
roomManager <avg> | roomState <avg> (<доля>% от roomManager)
taskGen <avg> | TaskSystem <avg> | spawn <avg> | lab <avg> | towers <avg> | link <avg> | factory <avg> | powerSpawn <avg>
роли (топ-5): <роль> <avg> | ...
комнаты: <комната> <avg> | ...
```

Дополнительно вручную (когда угодно) из консоли игры:

```js
require("cpuMonitor").reportProfile(); // та же строка сводки
JSON.stringify(Memory.cpuStats.profile); // полный дамп накопленного профиля
```

### 2.4 Как отключить/удалить инструментализацию

- **Решение по итогам задачи:** профилирование **оставлено включённым** (`CPU.PROFILE_ENABLED = true`) —
  его измеренная цена мала (раздел 4.1: накладные расходы `runRoom` + замер = 0.1249 мс/тик, 1.60 % от
  `roomManager`, из которых адресный замер `getUsed()` ≈0.10 мс/тик на 46 крипов), а без него нечем
  проверять эффект следующих оптимизаций. Отключать/делать opt-in — в конце этапа оптимизаций (Задача 5).
- выключить сбор, не удаляя код: `CPU.PROFILE_ENABLED = false` в `constants.js` (сбор и печать прекращаются);
- сбросить только замеры: `delete Memory.cpuStats.profile`;
- сбросить всю статистику вместе с существующей: `delete Memory.cpuStats`;
- полное удаление — удалить в `cpuMonitor.js` секцию «ПРОФИЛИРОВАНИЕ ROOM MANAGER», вызовы
  `accumulateProfile/flushProfile/reportProfile` в `endTick`, два `trackRole` в `room.manager.js:run`
  и `CPU.PROFILE_*` в `constants.js` (`PROFILE_ENABLED`/`PROFILE_REPORT_INTERVAL`), после чего
  `trackRole` можно вернуть к прежнему виду (без `return`).

### 2.5 Как снять данные для этого отчёта (живой шард)

Порядок для оператора:

1. задеплоить проект (текущий `Gruntfile.js`: ветка `test`);
2. дать боту набрать статистику. **Рекомендуемый период измерения: не менее 2–3 суток
   (≈ 20 000–30 000 тиков).** Минимум для устойчивых средних — 10 000 тиков
   (`samples` в `Memory.cpuStats.profile`);
3. один раз выполнить в консоли игры сниппет ниже — он печатает **готовые markdown-таблицы**
   для разделов 3–5 этого файла (`avg CPU/тик` = `sum / samples`, `max` = максимум за один тик):

```js
(() => {
  const p = Memory.cpuStats && Memory.cpuStats.profile;
  if (!p || !p.samples) return "Нет данных: Memory.cpuStats.profile пуст";
  const s = p.samples;
  const avg = e => (e ? e.sum / s : 0);
  const line = (label, e) =>
    "| " +
    label +
    " | " +
    avg(e).toFixed(3) +
    " | " +
    (e ? e.max.toFixed(3) : "-") +
    " | " +
    (e ? e.count : 0) +
    " |";
  const main = [
    ["средний CPU room.manager", "roomManager"],
    ["buildRoomState", "roomState"],
    ["генерация задач (taskManager)", "taskManager"],
    ["выполнение Task System (worker)", "worker"],
    ["tower logic (towers)", "towers"],
    ["link manager", "linkManager"],
    ["factory manager", "factoryManager"],
    ["powerSpawn manager", "powerSpawnManager"],
    ["lab manager", "labManager"],
    ["spawn manager", "spawnManager"],
  ];
  const known = main.map(m => m[1]);
  const rows = main.map(m => line(m[0], p.blocks[m[1]]));
  const roles = Object.keys(p.blocks)
    .filter(
      n =>
        known.indexOf(n) === -1 &&
        n.indexOf("Manager") === -1 &&
        n !== "terminalNetwork",
    )
    .sort((a, b) => p.blocks[b].sum - p.blocks[a].sum);
  const rooms = Object.keys(p.rooms).sort(
    (a, b) => p.rooms[b].sum - p.rooms[a].sum,
  );
  let out =
    "период: с тика " +
    p.startTick +
    " по " +
    Game.time +
    " (" +
    (Game.time - p.startTick + 1) +
    " тиков), замеров: " +
    s +
    ", крипов: " +
    Object.keys(Game.creeps).length +
    "\n\n" +
    "| Блок | avg CPU/тик | max CPU/тик | тиков активности |\n|---|---|---|---|\n" +
    rows.join("\n") +
    "\n";
  out +=
    "\n| Роль | avg CPU/тик | max CPU/тик | тиков активности |\n|---|---|---|---|\n" +
    roles.map(n => line(n, p.blocks[n])).join("\n") +
    "\n";
  out +=
    "\n| Комната | avg CPU/тик | max CPU/тик | тиков активности |\n|---|---|---|---|\n" +
    rooms.map(n => line(n, p.rooms[n])).join("\n") +
    "\n";
  const rm = avg(p.blocks.roomManager);
  out +=
    "\nroomState / roomManager = " +
    (rm > 0 ? ((avg(p.blocks.roomState) / rm) * 100).toFixed(1) + "%" : "n/a");
  return out;
})();
```

4. вставить полученные таблицы и период в разделы 4.1–4.7 ниже;
5. доля каждого блока считается как `avg_блока / avg_roomManager` (обе величины — фактические замеры,
   никаких «ожидаемых процентов»);
6. «накладные расходы» `runRoom` (не отнесённые ни к одной подсистеме) считаются как
   `Σ room:* − (taskManager + worker + все роли + towers + linkManager + factoryManager + powerSpawnManager + labManager + spawnManager)`
   — это одновременно стоимость самого измерения (`trackRole` вокруг каждого крипа и каждой подсистемы,
   2 × `Game.cpu.getUsed()` на вызов) и «пустая» работа менеджера между подсистемами.
   Эту величину обязательно указывать в выводах — она входит в CPU `room.manager` и раньше нигде не измерялась.

### 4.8 Адресные замеры (in-loop): из чего состоит цена ролей

Чтобы понять, *что именно* внутри ролей даёт измеренную долю, на живом шарде выполнены адресные замеры
(без правки репозитория — только консольные обёртки-счётчики, которые вызывают оригиналы; после замера
все патчи сняты):

| Что мерили                                                                  | Результат (мс на вызов) | Как мерили                                                             |
| --------------------------------------------------------------------------- | ----------------------: | ---------------------------------------------------------------------- |
| `creep.harvest(source)` — реальный вызов (минёр, тело 22 части)              |        **0.2125**       | обёртка `Creep.prototype.harvest`, 10 вызовов/тик, 2 тика              |
| `creep.harvest()` — ремоут-минёр (тело 12 частей)                            |        **0.2085**       | та же обёртка, разбивка по `body.length`                               |
| `creep.harvest()` — mineralMiner (тело 15 частей)                            |        **0.131**        | та же обёртка                                                          |
| `creep.transfer()` — реальный вызов                                          |          0.081          | обёртка `Creep.prototype.transfer` (3 вызова)                          |
| `Game.getObjectById()` — 1-й и 2-й вызов                                     |        0.0014 / 0.0007  | адресный замер внутри живого цикла (клон роли на 2 крипа/тик)          |
| `creep.store.getFreeCapacity()`                                              |          0.0067         | там же                                                                |
| `creep.pos.isEqualTo()`                                                      |          0.001          | обёртка `RoomPosition.prototype.isEqualTo` (21 вызов/тик)              |
| «пустой» `Game.cpu.getUsed()`                                                |          0.0009         | контроль: сам механизм измерения не создаёт «фантомного» CPU           |
| Обёртка-пустышка вместо `role.miner.run` (без логики, только `trackRole`)     |          0.0010–0.0017  | «no-op» эксперимент: патч `role.miner.run = function(){}` на 3 тика     |

Вывод раздела 4.8 (проверен дважды — обёрткой и бакетом):

1. **Бакет `miner` — это реальная работа, а не накладные расходы замера.** При подмене
   `role.miner.run` пустышкой бакет `miner` перестаёт расти (+0.0097 мс/тик на 10 крипов), а
   `roomManager` падает примерно на 2.2 мс/тик; после снятия патча бакет возвращается к 2.29 мс/тик.
2. **Почти всё в бакете `miner` (2.29 из 2.29 мс) — это `creep.harvest()`**: 10–12 вызовов × ≈0.21 мс.
   `off-spot` (то есть `travelTo`) в замере = 0, `findInRange` вызывается один раз за ~5 тиков
   (кэш `memory.sourceId` работает).
3. **Геттеры дешёвы (0.001–0.007 мс), «действия» (action-методы) — дороги (0.08–0.21 мс).**
   Отсюда практическое правило для оптимизаций: CPU определяется **числом вызовов методов-действий**
   (`harvest`, `transfer`, `move`, `repair`, …), а не объёмом JS-логики и не количеством операций
   внутри ролей. Это же объясняет, почему воркеры дёшевы (0.0836 мс/крип): у них ~1 действие на крипа
   за тик, а у минёра — `harvest` каждый тик каждым крипом.

Важная оговорка: замер через консоль **не** показывает эту цену (0.0105 мс на крипа), потому что
консольный вызов `harvest` попадает в «уже собранный за тик» путь и возвращается почти сразу.
Числа выше — из живого цикла (бакет профиля и адресные обёртки внутри тика), им и надо доверять.

Пики, которые были заранее заявлены как ожидаемые, сверены с данными: тик скана стен/валов
(`Game.time % TOWER.WALL_SCAN_INTERVAL === 0`, он же `REPAIR_INTERVAL`) виден в `towers`
(`max` 3.939 против `avg` 0.2152); «холодный» тик после Global Reset (пересборка `scanner`-кэша,
`STRUCTURE_CACHE_TTL = 1000`) виден в `roomManager` 28.089 и `roomState` 6.583.

## 5. Краткий вывод: что фактически является главным потребителем CPU

Раздел заполнен по заранее зафиксированному правилу (пункты 1–5 ниже — то же правило, что было в
документе до замеров, добавлены только фактические значения).

1. **Главный потребитель** — блок с наибольшим `avg CPU/тик`: **`miner` = 2.2914 мс/тик, 29.34 % от
   `roomManager`** (18.9 % от тика в 12.12 мс).
2. Первое место **не** занимает `roomState`: его доля **9.46 %**, то есть **гипотеза аудита о ≥ 40 %
   опровергнута фактами**. `roomState` — 6-й по стоимости блок, дальше оптимизировать его радикально
   (в отрыве от остального) смысла мало: даже полное устранение даёт ≤0.74 мс/тик (≈6 % тика).
3. Роли + `worker` действительно главная группа: **роли 5.0008 мс/тик (64.03 %)**, ещё `taskManager`
   0.9919 (12.70 %) — то есть роли + генерация задач = **5.9927 мс/тик (76.73 %)**, а роли вместе со
   всеми семью комнатными подсистемами (spawn/lab/task/towers/link/factory/powerSpawn) — **6.9311 мс/тик
   (88.74 %)**.
4. Накладные расходы `runRoom` + **сам замер** = **0.1249 мс/тик (1.60 %)** — это **ниже порога 10–15 %**:
   роль-мониторинг (`2 × getUsed()` на крипа) стоит измеримо мало (адресный замер: `getUsed()` ≈0.0009 мс,
   то есть ≈0.10 мс/тик на 46 крипов). Убирать его не срочно; отключать/делать opt-in — в конце
   оптимизаций, а не вместо них.
5. Подсистемы из 4.5 дороже 1 %: `towers` 2.76 % (уже оптимизированы) и `linkManager` 1.56 %;
   `factoryManager` 0.72 % и `powerSpawnManager` 0.32 % — **трогать не нужно** (фичи к тому же выключены).

**Итоговая строка вывода:** *главный потребитель — не `roomState`, а «действия» крипов: одна роль
`miner` (10–12 вызовов `creep.harvest()` в тик) даёт 29.3 % `roomManager`; почти вся её цена —
сам вызов action-метода (≈0.21 мс), а не JS-логика роли. Роли + генерация задач = 76.7 %
(роли вместе со всеми подсистемами — 88.7 %), `roomState` = 9.46 %, измерительный слой = 1.60 %.*

## Приложение 2. Как воспроизвести замеры из разделов 3–4.8

Чтение готового профиля (не влияет на игру, токен — тот же, что в `Gruntfile.js`):

```bash
# профиль целиком
node -e 'const{ScreepsAPI}=require("screeps-api");const a=new ScreepsAPI({token:"<TOKEN>"});a.memory.get("cpuStats.profile","shard3").then(r=>console.log(JSON.stringify(r.data,null,1)))'

node -e 'const{ScreepsAPI}=require("screeps-api");const a=new ScreepsAPI({token:"<TOKEN>"});a.memory.get("cpuStats","shard3").then(r=>console.log(JSON.stringify(r.data)))'
```

Короткий сниппет для пересчёта «avg/max/доля» из профиля — раздел 2.5 (он же печатает markdown-таблицы).

Адресные замеры (4.8) сделаны **только через консоль** и не требуют деплоя: команда в консоли игры
задаёт обёртку-счётчик (например `Creep.prototype.harvest` → считать `Game.cpu.getUsed()` до/после и
складывать в `global.__hb`), снимок счётчиков пишется в `Memory.__…` и вычитывается через `memory.get`,
после чего обёртка возвращается к оригиналу, а временный ключ удаляется. Альтернатива без консоли —
читать живое heap-окно профиля: `require("cpuMonitor").profileWindow` виден с шарда в консоли и
обновляется **каждый тик** (в отличие от `Memory.cpuStats.profile`, который сбрасывается раз в
`CPU.PROFILE_REPORT_INTERVAL` тиков).

Реплики ключевых замеров (консоль игры; после каждого пункта — восстановление):

```js
// (a) живое heap-окно профиля (каждый тик): samples и суммы по бакетам
require("cpuMonitor").profileWindow

// (b) цена creep.harvest() в живом цикле, в разбивке по размеру тела
global.__hb={};global.__o.h=Creep.prototype.harvest;
Creep.prototype.harvest=function(){var k=this.body.length,s=global.__hb[k]||(global.__hb[k]={c:0,t:0,mx:0});var t0=Game.cpu.getUsed();var r=global.__o.h.apply(this,arguments);var d=Game.cpu.getUsed()-t0;s.c++;s.t+=d;if(d>s.mx)s.mx=d;return r};
// ...через 2–3 тика:  Memory.__hb                                  → прочитать через memory.get
// восстановление:    Creep.prototype.harvest=global.__o.h; delete Memory.__hb

// (c) «no-op» эксперимент: доказать, что бакет — реальная работа, а не накладные расходы замера
global.__o.mp=require("role.miner").run;require("role.miner").run=function(){};
// ...через 3 тика бакеты miner/roomManager в профильном окне перестают расти
// восстановление:    require("role.miner").run=global.__o.mp
```

Учтите: замер «того же действия» из консоли (вне живого цикла) даёт в разы меньшие числа — в момент
вызова консоли действие за этот тик уже выполнено, и вызов уходит по «дешёвому» пути. Именно поэтому
все числа отчёта сняты из живого цикла (бакеты профиля + обёртки внутри тика).

**Что в ходе этой задачи менялось:** в репозитории — ничего (все замеры read-only и через консоль).
На живом шарде временно существовали ключи `Memory.__task0`, `Memory.__t0b/__t0c/__t0d`, `Memory.__w`,
`Memory.__hb2/__hb3/__hb4/__hb5`, `Memory.__tick`, `Memory.__p1/__p2`, `Memory.__m` — все удалены;
консольные патчи (`role.miner.run`, `Creep.prototype.harvest/transfer/travelTo`,
`RoomPosition.prototype.findInRange/isEqualTo`, `Game.getObjectById`) сняты сразу после замеров.
Код на шарде остался тем же (дополнительно подтверждено сверкой md5 с HEAD, раздел 3).

Проверено после всех зондов (скрипт-проверка, тик `83039770`): `Creep.prototype.harvest/transfer/travelTo`,
`RoomPosition.prototype.findInRange/isEqualTo`, `Game.getObjectById` и `role.miner.run` — оригинальные
(в их коде нет обёрток-счётчиков), `CPU.PROFILE_ENABLED = true`, окно профиля продолжает наполняться
(`profileWindow.samples` растёт каждый тик). В `Memory` остались два не относящихся к этой задаче
диагностических ключа от предыдущих сессий — `__wins` (используется сниппетом «тёплых окон» в
`docs/TOWER-CPU-OPTIMIZATION.md`) и `__chkTick`; при необходимости удаляются вручную:
`delete Memory.__wins; delete Memory.__chkTick`.
