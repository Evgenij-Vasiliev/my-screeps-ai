# LAB-WORKER-CPU-OPTIMIZATION

**Снижение CPU блока `labWorker` (роль `lab.worker`)** — адресный разбор на живом шарде, внесённые изменения, контрольные замеры.

- **Дата:** 18.09.2026
- **Основание:** `docs/PROJECT_AUDIT_AND_ROADMAP.md` (порядок «по измеренно главному потребителю») и `docs/CPU-PROFILE-ROOM-MANAGER.md`, раздел 6. После закрытия `miner` (29.34 %), `remoteManager` (24.69 %), Task System (`taskManager` 12.70 % + `worker` 10.70 %), `harvester` и `towers` крупнейшим **неразобранным** блоком оставался `labWorker` — **13.8 %** `roomManager` (0.9409 мс/тик на окне 11 885 тиков), то есть больше `roomState` (9.46 %), который в роадмапе стоит следующим пунктом.
- **Область правки:** `lab.worker.js` (вся логика роли), `constants.js` (новая секция `LAB_WORKER`), новый офлайн-харнесс `tests/lab.worker.test.js`, новый измерительный инструмент `tests/live.profile.labworker.js`. Поведение других подсистем не менялось.
- **Живой шард:** `shard3`, ветка `test` (`npx grunt screeps`); окна замеров — тики `83057278…83057622` (до и после деплоя).
- **Проверки:** `node --check` — OK; `npx tsc --noEmit -p jsconfig.json` — exit 0; `npx eslint .` — 16 проблем (12 errors / 4 warnings), ровно как до правки; `node tests/lab.worker.test.js` — 25/25.

## 1. Как измерялось

Второго мониторинга CPU не создавалось — использован тот же метод, что в `docs/REMOTE-CPU-OPTIMIZATION.md`, раздел 1:

| Что | Как |
| --- | --- |
| Бакет `labWorker` целиком | `Memory.cpuStats.profile` (накопительное окно: `startTick`/`samples`/`sum`/`max`) и живое heap-окно `require("cpuMonitor").profileWindow` |

| Функциональный контроль | консольные пробы состояния лаб и рюкзаков `labWorker` через API (только чтение) |

Инструмент: `tests/live.profile.labworker.js` (`MODE=install|snapshot|restore`), счётчики живут в `global`, снимок переносится в `Memory.__lw` и вычитывается через `screeps-api`. Формулы — как в ТЗ №0: `avg = sum / samples`, доля = `avg_блока / avg_roomManager`.

## 3. Причина: рейс за рейсом по 5 единиц реагента

Приоритеты роли «долить реагент» смотрели только на «лаба не полна» (`< 3000`), а количество к забору считалось как **дефицит лабы**:

```js
if ((lab1.store[config.reagent1] || 0) < LAB_CAPACITY) {
  const needed = LAB_CAPACITY - (lab1.store[config.reagent1] || 0);
  ...
  creep.memory.amount = Math.min(needed, src.store[config.reagent1], creep.store.getFreeCapacity());
}
```

Реакция расходует 5 единиц реагента за тик, поэтому лаба почти всегда «не полна ровно на 5» — и дефицит получался крошечным. Живая проба в самой нагруженной комнате (`E35S39`, тройка `labs2` = `O + H → OH`) подтвердила это буквально:

```text
lab1 (O): 3000     lab2 (H): 2995     reactor (OH): 35
labWorker: store {H: 5}, task load_lab2, amount 5, position 29,16
```

То есть крип **везёт ровно 5 единиц** и на каждые 5 единиц делает полный рейс «хранилище → лаба». Батарея крипа — 500 единиц (тело `{carry: 10}`), то есть 99 % вместимости простаивало, а каждый рейс — это `travelTo` с пересчётом пути, стоимость которого и есть бакет роли.

Сопутствующие находки того же рода:

1. `unload_reactor` срабатывал при `product >= 50` — при расходе 5/тик это рейс каждые 10 тиков на **каждый** реактор (в комнате с тремя тройками — 0.3 рейса/тик), а вывозилось за рейс всего 50 единиц.
2. Действия вызывались до проверки расстояния (`if (act() === ERR_NOT_IN_RANGE) travelTo()`): каждый тик поездки уходил «пустой» `withdraw`/`transfer` с `ERR_NOT_IN_RANGE` (0.03–0.07 мс).
3. Перебор конфигов (`getRotatedConfigs`) выполнялся каждый тик без задачи, и **каждый** перебор писал `room.memory.labWorkerIndex` — Memory «пачкалась» каждый тик ради счётчика.

## 4. Внесённые изменения

| Файл | Что и почему |
| --- | --- |
| `constants.js` | новая секция **`LAB_WORKER`**: `CAPACITY: 3000` (единая точка правды), `PRODUCT_UNLOAD_AT: 250` (было 50 — рейсов в 5 раз меньше, до переполнения 3000 далеко), `IDLE_SCAN_INTERVAL: 3` (перебор конфигов без задачи) |
| `lab.worker.js` | (1) **гистерезис дозаправки**: задача `load_lab1`/`load_lab2` создаётся, только если дефицит лабы **не меньше свободного места в рюкзаке крипа** (или крип уже везёт этот реагент — тогда задачу даём всегда, чтобы сдал привезённое). За рейс крип берёт полный рюкзак и возвращается пустым; лаба держится в коридоре `[CAPACITY − рюкзак, CAPACITY]` — для реакции это буфер на сотни тиков; (2) порог выгрузки продукта — `LAB_WORKER.PRODUCT_UNLOAD_AT`; (3) новый хелпер **`actIfNear`**: действие вызывается только когда крип уже рядом, иначе — `travelTo`; (4) **троттлинг перебора**: крип без задачи обходит тройки не чаще `IDLE_SCAN_INTERVAL` тиков; (5) указатель round-robin переехал в **heap** (`global._labWorker.idx`), `room.memory.labWorkerIndex` больше не пишется; (6) ротация конфигов собирается одним проходом без `slice+concat`; (7) `creep.say("❌ нет конфига")` — не чаще раза в 50 тиков (дефект №17 аудита) |
| `tests/lab.worker.test.js` | новый офлайн-харнесс (25 проверок): мок `Store` как в игре (отсутствующий ресурс = 0, `for..in` видит только лежащие ресурсы), проверки гистерезиса, полного рюкзака, сдачи привезённого, отсутствия «пустых» действий, троттлинга, порога продукта, round-robin и `clear_lab` |
| `tests/live.profile.labworker.js` | новый измерительный инструмент (обёртки в живом VM → снимок в `Memory` → чтение через API) |

**Почему это безопасно:** вариант «гистерезис» не создаёт излишков в рюкзаке. Раз новый рейс начинается только при дефиците ≥ рюкзака, крип всегда сдаёт весь привезённый ресурс и возвращается пустым — нет ситуации «везёт один реагент, а задача про другой», из-за которой `withdraw` вернул бы `ERR_FULL` и задача зависла. Единственное исключение — крип, которому реагент дали в прошлой версии кода: ветка «уже везёт» доводит его до лабы.

**Риск по реакции:** буфер в лабе не опускается ниже `CAPACITY − рюкзак` (2500 из 3000), то есть на 500 тиков потребления при расходе 5/тик. Раньше буфера фактически не было (лаба доливалась каждый тик), но «жизнь» реакции от этого не зависела: реакция останавливается только при нулевом реагенте.

## 5. Контрольные замеры после правки

**Деплой:** `npx grunt screeps` (ветка `test`); сверка `tests/live.diff.deployed.js` — 40/40 модулей на шарде совпадают с локальными.

**Функциональный контроль (живые пробы, только чтение):**

| Что проверялось | Результат |
| --- | --- |
| Роль не начинает рейс при малом дефиците | сразу после деплоя `E35S39.labs2` = `O 3000 / H 2995`, все `labWorker` пусты и без задачи — при старом коде каждый такой тик порождал рейс |
| Реакция не голодает | активные тройки держат реагенты в коридоре ≈2500…3000 (`E35S39.labs2` O 2990 / H 2985; `E37S38.labs2` O 2990 / H 2980) — реакция идёт непрерывно |
| Работа при отсутствии реагента | там, где реагента нет в хранилище и терминале (`LHO2`, `KH`, `K`, `O` = 0), роль корректно простаивает — это дефицит поставки, а не регрессия |
| Round-robin и `clear_lab` | проверены офлайн-харнессом (сценарии 7–8) |

**Окно профиля «после» (тот же `Memory.cpuStats.profile` / живое heap-окно `cpuMonitor.profileWindow`; окно начато деплоем, тик 83057533, 68 замеров):**

| Метрика | До | После | Изменение |
| --- | ---: | ---: | ---: |
| `labWorker`, мс/тик | 0.9409 | **0.2130** | **−77 %** |
| `max`, мс | 14.849 | **2.045** | −86 % |
| доля от `roomManager` | 13.8 % | **3.4 %** | — |
| `roomManager`, мс/тик (масштаб) | 6.8151 | 6.2053 | — |
| `miner` / `worker` / `roomState` для масштаба | 1.3105 / 1.0445 / 0.7357 | 1.3754 / 1.0666 / 0.8346 | — |

Экономия ≈ **0.73 мс/тик** — это ~6 % CPU тика (при измеренном тике ~11.7 мс) и ~11 % `roomManager`.

**Почему в окне «после» ноль рейсов, и почему это не занижает оценку.** Реактор после реакции уходит в `cooldown` 10 тиков, поэтому реакция идёт не чаще раза в 10 тиков и расходует 5 единиц реагента — то есть лаба «худеет» на ~0.5 единицы за тик. Запас в 500 единиц (один рюкзак) покрывает ~1000 тиков, поэтому в коротком окне (68 тиков) рейс просто не был нужен. Старый код делал рейс на **каждую** реакцию (раз в 10 тиков, по 5 единиц): пока крип ехал ~10 тиков «туда-обратно», приходила следующая порция, поэтому в активной комнате он был в дороге практически непрерывно (измерено 1.7 вызова `travelTo` в тик). Новый — примерно **один рейс на 1000 тиков** на поток реагента, то есть снижение числа рейсов на два порядка; замеренное значение (0.213 мс/тик) — это установившаяся стоимость роли, которой подавляющую часть времени делать нечего.

**Адресный замер «после» (тот же инструмент `tests/live.profile.labworker.js`; окно 54 тика, тик 83057609 → 83057663, 270 запусков роли — все пять крипов в комнатах, где дефицит реагента меньше рюкзака):**

| Показатель | До (окно 11 тиков) | После (окно 54 тика) |
| --- | ---: | ---: |
| `travelTo`, вызовов/тик | 1.7 | **0** |
| `withdraw` + `transfer`, вызовов/тик | 2.0 | **0** |
| запусков с задачей | 38 % | **0** (все 270 — idle) |
| переборов конфигов, /тик | ~5–12 | **1.6** (≈ 5 крипов / `IDLE_SCAN_INTERVAL`) |
| всего бакета, мс/тик | 0.884 | **0.203** |
| `max` одного запуска, мс | 0.465 | 0.114 |

То есть в установившемся режиме (реагенты выше порога дозаправки) роль **не делает вообще ничего** — вместо
«рейс на каждые 5 единиц» это ноль действий и один перебор конфигов раз в 3 тика на крипа; рейсы появляются
только когда дефицит дорос до рюкзака.

## 6. Что сознательно НЕ сделано

- **Маршрут внутри узла лаб не менялся.** `travelTo` остаётся основным инструментом перемещения; после батчинга его доля резко падает, но если понадобится следующий шаг — это уже работа по Traveler (общая для всех ролей), а не по `lab.worker`.
- **Тела `labWorker` (`{carry: 10, move: 10}`) не менялись.** Батарея 500 единиц уже даёт большой запас; увеличение тела — это энергозатраты, а не CPU-выигрыш.
- **Квоты спавна `labWorker` не трогались** (дефект №17 аудита: роль спавнится в комнатах без конфигов лаб). Это задача 7 роадмапа; сейчас в империи 5 комнат, и во всех есть конфиги.
- **`terminalNetwork` не трогался**, хотя он использует `labWorker.getConfigs` — сигнатура сохранена без изменений.

## 9. Итог одной строкой

Бакет `labWorker` (0.94 мс/тик, 13.8 % `roomManager`) был почти целиком «поездками»: крип возил **по 5 единиц реагента** (свежая порция реакции) и делал на каждые 5 единиц полный рейс «хранилище → лаба»; введён гистерезис дозаправки (рейс начинается при дефиците ≥ рюкзака, за рейс — полный рюкзак), порог выгрузки продукта поднят с 50 до 250, действия вызываются только рядом, перебор конфигов без задачи троттлится, указатель round-robin перенесён из Memory в heap.
