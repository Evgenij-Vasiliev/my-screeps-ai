# TASK SYSTEM v3.0

## Development Rules

---

# 1. Назначение

Настоящий документ определяет обязательные правила разработки Task System v3.0.

Все изменения архитектуры и реализации должны соответствовать данным правилам.

При возникновении противоречий между удобством реализации и настоящими правилами приоритет имеют настоящие правила.

---

# 2. Главный принцип

Работающая Империя важнее любой архитектуры.

Ни одно изменение не должно ухудшать стабильность действующей Империи.

---

# 3. Поэтапное внедрение

Любое изменение внедряется небольшими независимыми этапами.

Каждый этап обязан:

- быть законченным;
- быть работоспособным;
- быть протестированным;
- иметь возможность отката.

Запрещается внедрение больших незавершённых изменений.

---

# 4. Принцип единственной ответственности

Каждый компонент отвечает только за одну задачу.

Компонент не должен принимать решения, относящиеся к ответственности другого компонента.

---

# 5. Централизация управления

Архитектурные решения принимаются только центральными компонентами.

Dispatcher принимает решения.

Scheduler определяет политики.

Assignment Engine назначает исполнителей.

Registry хранит состояние.

Исполнители выполняют работу.

---

# 6. Единый источник истины

Каждая сущность имеет только одно место хранения.

Запрещается дублировать информацию в нескольких структурах Memory.

При необходимости компонент получает данные из соответствующего Registry.

---

# 7. Запрет скрытых зависимостей

Компоненты взаимодействуют только через утверждённые интерфейсы.

Запрещается:

- обращаться к внутренним структурам другого компонента;
- изменять его внутреннее состояние напрямую;
- использовать неутверждённые поля Memory.

---

# 8. Расширение без изменения ядра

Добавление новой функциональности должно происходить путём:

- добавления новых типов задач;
- новых событий;
- новых политик;
- новых диагностических модулей.

Запрещается изменять ядро системы без архитектурной необходимости.

---

# 9. Feature Switches

Любой новый компонент должен поддерживать возможность включения и отключения через Feature Switches.

Компонент, не поддерживающий централизованное управление, считается незавершённым.

---

# 10. Совместимость

Во время миграции Task System v2.0 и Task System v3.0 должны сосуществовать.

Новые компоненты не должны нарушать работу существующей системы.

---

# 11. Производительность

При разработке необходимо учитывать ограничения CPU Screeps.

Предпочтение отдаётся:

- повторному использованию результатов вычислений;
- централизованным проходам по данным;
- простым структурам;
- минимальному количеству операций за тик.

Не допускается добавление тяжёлых вычислений без объективной необходимости.

## 11.1. Обязательные правила по CPU

Правила ниже введены по итогам оптимизации 27.09.2026
(`docs/CPU-OPTIMIZATION-PLAN.md`, `docs/CPU-BASELINE.md`) и проверяются
автоматически тестом `tests/rules.test.js`.

**1. Ни одного `Game.market.*` вне throttle и без кэша на тик.**

`Game.market.getAllOrders` стоит 0.16–0.89 CPU за вызов (замерено), а проход рынка
обходит все терминалы. Обращение к рынку допускается только:
- не чаще `MARKET.INTERVAL` тиков (`constants.js`);
- через кэш на текущий тик (`getOrders`), а не прямым вызовом.

**2. Ни одного `Object.values(Game.*)` в коде, исполняемом на каждого крипа.**

`Object.values(Game.creeps)` стоит ~0.0035 CPU (замерено). Такой вызов в теле роли
умножается на число крипов. Для обхода использовать `for...in` или общий индекс,
построенный один раз за тик.

**3. `Memory` — только то, что переживает рестарт, и только при смене значения.**

`Memory` сериализуется целиком каждый тик, поэтому стоимость ∝ её объёму.
- статичные данные (кэш структур, индексы, агрегаты) живут в `global`;
- поле верхнего уровня, начинающееся с `__`, считается **временным** и вычищается
  в `empire.js` каждый тик (отладка — через `Memory.keepTemp = true`);
- значение пишется только если оно изменилось.

**4. Поиск — без `room.find` в горячем пути.**

В коде, исполняемом каждый тик или на каждого крипа, использовать кэш id
(`scanner.getStructureCache`, `scanner.getSitesByRoom`, индексы задач).
`room.find` допустим в момент построения кэша и в редких ветках
(раз в N тиков), где движок кэширует результат в пределах тика.

**5. Замер до и после.**

Любое изменение, затрагивающее горячий путь, сопровождается замером
`Memory.cpuStats` (поле `subsystems`) до и после. Разбивка по подсистемам
пишется монитором автоматически раз в `CPU.REPORT_INTERVAL` тиков.

---

# 12. Наблюдаемость

Каждый компонент должен быть пригоден для диагностики.

При необходимости его состояние должно быть доступно через Diagnostics.

Критические изменения должны фиксироваться Logging.

---

# 13. Обработка ошибок

Ошибки не должны приводить к остановке всей системы.

Компонент обязан:

- корректно сообщать об ошибке;
- сохранять целостность данных;
- позволять восстановление работы после устранения причины.

---

# 14. Документирование

Любое изменение архитектуры должно сопровождаться обновлением соответствующей архитектурной документации.

Не допускается расхождение между документацией и реализованной архитектурой.

---

# 15. Изменение архитектуры

Если реализация требует изменения архитектурных принципов, сначала обновляется архитектурный документ, затем утверждается Координатором, и только после этого допускается подготовка ТЗ и реализация.

Запрещается изменять архитектуру через код.

---

# 16. Критерии качества ТЗ

Каждое техническое задание должно:

- изменять только один архитектурный слой или один логически завершённый элемент;
- иметь чётко определённую цель;
- содержать критерии завершения;
- содержать критерии проверки;
- не требовать последующих обязательных изменений для сохранения работоспособности.

---

# 17. Критерии готовности компонента

Компонент считается завершённым, если:

- выполняет только свою ответственность;
- интегрирован через утверждённые интерфейсы;
- поддерживает Feature Switches;
- отображается в Diagnostics;
- журналирует критические события при необходимости;
- не нарушает работу других компонентов;
- соответствует требованиям по CPU.

---

# 18. Архитектурная дисциплина

Запрещается:

- создавать новые менеджеры без архитектурного обоснования;
- дублировать функциональность существующих компонентов;
- переносить ответственность между компонентами без изменения архитектурной документации;
- вводить временные решения без плана их удаления.

Любое упрощение должно уменьшать сложность системы, а не скрывать её.

---

# 19. Роль участников проекта

**Координатор**

- определяет цели;
- утверждает архитектуру;
- принимает решения о внедрении.

**Архитектор**

- проектирует систему;
- поддерживает архитектурную документацию;
- готовит технические задания;
- контролирует соответствие архитектуре.

**Тактик**

- реализует утверждённые технические задания;
- не изменяет архитектуру самостоятельно;
- сообщает о выявленных архитектурных ограничениях.

---

# 20. Итоговый принцип

Task System v3.0 должна развиваться как единая система управления Империей.

Любое изменение должно повышать:

- управляемость;
- предсказуемость;
- наблюдаемость;
- устойчивость;
- расширяемость.

Если изменение делает систему сложнее, но не увеличивает её управляемость, оно не должно приниматься в проект.
