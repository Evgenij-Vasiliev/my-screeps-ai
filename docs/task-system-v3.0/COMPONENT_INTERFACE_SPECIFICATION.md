# TASK SYSTEM v3.0

## Component Interface Specification

---

# 1. Назначение

Настоящий документ определяет обязанности, зоны ответственности и интерфейсы компонентов Task System v3.0.

Документ не описывает реализацию.

Он определяет архитектурные контракты между компонентами.

Каждый компонент должен выполнять только свою задачу.

---

# 2. Общие принципы

Все компоненты:

- имеют единственную ответственность;
- работают через `Memory.taskSystem`;
- не изменяют внутреннее состояние других компонентов напрямую;
- взаимодействуют только через определённые интерфейсы;
- могут быть независимо отключены через Feature Switches.

---

# 3. Control Layer

## Назначение

Точка входа для команд Координатора.

---

## Ответственность

- получение команд управления;
- изменение режима Империи;
- изменение состояния рубильников;
- передача команд Dispatcher.

---

## Не отвечает за

- создание задач;
- назначение исполнителей;
- выполнение игровой логики.

---

## Предоставляет

- управление Империей;
- управление комнатами;
- управление ролями;
- управление подсистемами;
- управление задачами.

---

# 4. Empire Dispatcher

## Назначение

Центральный координатор Task System.

---

## Ответственность

- обработка событий;
- принятие решений;
- создание задач;
- отмена задач;
- изменение состояний задач;
- взаимодействие с Scheduler.

---

## Получает данные от

- Event Queue;
- Scheduler;
- Feature Switches;
- Control Layer.

---

## Передает данные в

- Task Registry;
- Logging;
- Diagnostics.

---

## Не отвечает за

- поиск исполнителей;
- выполнение задач;
- контроль зависаний.

---

# 5. Scheduler

## Назначение

Определяет, какие действия разрешены в текущем состоянии Империи.

---

## Ответственность

- анализ состояния Империи;
- применение политик;
- управление приоритетами;
- разрешение или запрет запуска задач.

---

## Использует

- состояние CPU;
- Bucket;
- энергию;
- режимы комнат;
- аварийный режим;
- глобальные политики.

---

## Не отвечает за

- создание задач;
- выбор исполнителей.

---

# 6. Task Registry

## Назначение

Единое хранилище задач.

---

## Ответственность

- регистрация задач;
- изменение состояния;
- поиск;
- хранение истории состояния.

---

## Не отвечает за

- принятие решений;
- выполнение задач;
- выбор исполнителей.

---

# 7. Assignment Engine

## Назначение

Назначение исполнителей.

---

## Ответственность

- выбор подходящего исполнителя;
- привязка задачи;
- снятие назначения;
- повторное назначение.

---

## Использует

- Task Registry;
- Executor Registry;
- Feature Switches.

---

## Не отвечает за

- создание задач;
- изменение политик;
- управление Империей.

---

# 8. Executor Registry

## Назначение

Единый реестр исполнителей.

---

## Ответственность

- регистрация исполнителей;
- хранение состояния;
- хранение назначений;
- обновление жизненного цикла.

---

## Не отвечает за

- поиск задач;
- принятие решений;
- диспетчеризацию.

---

# 9. Event Queue

## Назначение

Хранилище событий.

---

## Ответственность

- регистрация событий;
- очередь обработки;
- удаление обработанных событий.

---

## Не отвечает за

- создание задач;
- принятие решений.

---

# 10. Feature Switches

## Назначение

Единая система управления доступностью компонентов.

---

## Ответственность

- включение;
- отключение;
- блокировка;
- хранение причин отключения.

---

## Используется всеми компонентами.

---

# 11. Watchdog

## Назначение

Контроль выполнения.

---

## Ответственность

- обнаружение зависаний;
- контроль таймаутов;
- обнаружение потерянных исполнителей;
- инициирование повторного назначения;
- уведомление Diagnostics.

---

## Не отвечает за

- создание задач;
- выбор исполнителей.

---

# 12. Diagnostics

## Назначение

Мониторинг состояния системы.

---

## Ответственность

- сбор статистики;
- агрегирование данных;
- обнаружение проблем;
- предоставление отчётов.

---

## Не изменяет состояние системы.

---

# 13. Logging

## Назначение

Журналирование.

---

## Ответственность

Регистрация:

- создания задач;
- назначения;
- завершения;
- ошибок;
- отмен;
- аварий;
- изменений режимов.

---

## Не участвует в управлении.

---

# 14. Взаимодействие компонентов

```text
                    Control Layer
                           │
                           ▼
                  Empire Dispatcher
                    │            │
                    │            ▼
                    │       Scheduler
                    │
                    ▼
                 Task Registry
                    │
                    ▼
             Assignment Engine
                    │
                    ▼
             Executor Registry
                    │
                    ▼
                 Исполнители
```

Сервисные компоненты:

```text
Events ─────────► Dispatcher

Switches ───────► Все компоненты

Watchdog ───────► Registry

Diagnostics ────► Все компоненты

Logging ◄──────── Все компоненты
```

---

# 15. Запрещённые зависимости

Во избежание роста связанности запрещается:

- Dispatcher напрямую управлять исполнителями;
- Scheduler изменять задачи;
- Registry принимать архитектурные решения;
- Executor Registry искать задачи;
- Watchdog создавать новые задачи;
- Diagnostics изменять состояние системы;
- Logging участвовать в логике управления.

Каждый компонент работает только в пределах своей ответственности.

---

# 16. Принципы расширения

Добавление новой функциональности должно происходить без изменения существующих интерфейсов.

Расширение достигается путём:

- добавления новых типов задач;
- добавления новых событий;
- добавления новых политик Scheduler;
- добавления новых диагностических отчётов;
- добавления новых рубильников управления.

Архитектурные контракты между компонентами должны оставаться стабильными.

---

# 17. Итоговая модель

Task System v3.0 строится вокруг центрального Dispatcher, который принимает решения, опираясь на политики Scheduler, события Event Queue и ограничения Feature Switches.

Task Registry хранит состояние задач, Assignment Engine назначает исполнителей, Executor Registry управляет их жизненным циклом, а Watchdog, Diagnostics и Logging обеспечивают контроль, наблюдаемость и устойчивость системы.

Такое разделение обязанностей обеспечивает слабую связанность компонентов, возможность независимого тестирования, постепенного внедрения и безопасного развития архитектуры без нарушения работы действующей Империи.
