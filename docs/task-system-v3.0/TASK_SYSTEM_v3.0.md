# TASK SYSTEM v3.0

## Архитектурный документ (Architecture Specification)

---

# 1. Назначение

Task System v3.0 является центральной системой управления Империей.

Она не является простой очередью задач.

Task System v3.0 представляет собой единый слой управления, через который осуществляется работа всех автоматических подсистем Империи.

Все новые подсистемы Империи должны интегрироваться именно с Task System v3.0.

---

# 2. Цели

Система должна обеспечивать:

- централизованное управление Империей;
- единый жизненный цикл задач;
- единый жизненный цикл исполнителей;
- диспетчеризацию;
- планирование;
- безопасное распределение задач;
- контроль выполнения;
- диагностику;
- журналирование;
- аварийное восстановление;
- возможность постепенного расширения без изменения ядра.

---

# 3. Основные принципы

## 3.1 Работающая Империя важнее архитектуры

Ни одно изменение не должно останавливать работу Империи.

---

## 3.2 Минимально необходимая сложность

Каждый новый компонент должен решать отдельную задачу.

Запрещается создавать менеджеры без необходимости.

---

## 3.3 Расширяемость

Добавление нового типа задач не должно требовать изменения существующей архитектуры.

---

## 3.4 Управление вместо жёсткой логики

Подсистемы сообщают о происходящих событиях.

Task System принимает решение о дальнейших действиях.

---

# 5. Компоненты системы

## 5.1 Control Layer

Верхний уровень управления.

Принимает команды Координатора.

Примеры:

- запуск;
- остановка;
- аварийный режим;
- отключение подсистем;
- изменение режимов работы.

Control Layer не содержит игровой логики.

---

## 5.2 Empire Dispatcher

Центральный диспетчер Империи.

Отвечает на вопрос:

> Что должно происходить сейчас?

Основные обязанности:

- разрешение создания задач;
- отмена задач;
- управление подсистемами;
- применение политик Империи;
- взаимодействие с Scheduler.

---

## 5.3 Scheduler

Планировщик.

Определяет:

- какие задачи разрешено запускать;
- какие задачи необходимо отложить;
- какие задачи запрещены.

Scheduler принимает решения на основе состояния Империи.

Примеры факторов:

- CPU;
- Bucket;
- энергия;
- аварии;
- приоритеты;
- режим комнаты.

---

## 5.4 Task Registry

Единый реестр задач.

Каждая задача имеет одинаковую структуру.

### Возможные состояния

- Created
- Waiting
- Ready
- Assigned
- Running
- Completed
- Failed
- Cancelled
- Timeout
- Disabled

---

## 5.5 Assignment Engine

Назначает исполнителей.

Использует:

- приоритет;
- доступность;
- расстояние;
- состояние исполнителя;
- ограничения задачи.

---

## 5.6 Executor Registry

Хранит информацию обо всех исполнителях.

Состояния исполнителя:

- Idle
- Moving
- Working
- Blocked
- Sleeping
- Disabled
- Dead

---

## 5.7 Watchdog

Следит за выполнением задач.

Контролирует:

- отсутствие прогресса;
- превышение времени;
- потерю цели;
- смерть исполнителя;
- невозможность завершения.

При необходимости:

- снимает задачу;
- переводит в ожидание;
- создаёт повторное назначение;
- сообщает Diagnostics.

---

## 5.8 Diagnostics

Предоставляет информацию о состоянии системы.

Примеры:

- количество задач;
- количество исполнителей;
- зависшие задачи;
- перегрузка;
- отключённые модули;
- ошибки.

Diagnostics не изменяет состояние Империи.

---

## 5.9 Logging

Фиксирует основные события.

Например:

- создание задачи;
- назначение;
- завершение;
- отмену;
- аварии;
- восстановление.

---

## 5.10 Feature Switches

Единая система управления.

Позволяет отключать без изменения кода:

- Империю;
- комнаты;
- менеджеры;
- роли;
- группы ролей;
- отдельных крипов;
- типы задач;
- отдельные задачи.

Все переключатели должны использовать единый механизм.

# 8. Рубильники управления

Система должна поддерживать мгновенное включение и отключение:

- всей Империи;
- комнаты;
- подсистемы;
- менеджера;
- роли;
- группы ролей;
- отдельного крипа;
- задачи;
- типа задач.

Все изменения выполняются без изменения исходного кода.

---

# 9. Требования к внедрению

Task System v3.0 внедряется поэтапно.

Каждый этап обязан:

- быть полностью обратимым;
- не нарушать работу существующей Империи;
- иметь возможность независимого тестирования;
- не требовать остановки игры.

На период миграции допускается совместная работа Task System v2.0 и Task System v3.0.

---

# 10. Требования к производительности

Архитектура должна учитывать ограничения Screeps.

При проектировании необходимо:

- минимизировать расход CPU;
- минимизировать количество проходов по объектам;
- избегать дублирования вычислений;
- использовать централизованные структуры данных;
- не выполнять тяжёлые операции каждый тик без необходимости.

---

# 11. Принципы развития

Новая функциональность должна реализовываться путём подключения новых типов задач и политик управления, а не перепроектирования ядра системы.

Ядро Task System v3.0 должно оставаться стабильным, компактным и независимым от логики отдельных подсистем Империи.

---

# 12. Итоговая концепция

Task System v3.0 является операционной системой Империи.

Её задача — не выполнять игровые действия напрямую, а централизованно принимать решения о том:

- что должно быть сделано;
- когда это должно быть сделано;
- кем это должно быть выполнено;
- можно ли выполнять это в текущем состоянии Империи;
- как система должна реагировать на изменения, ошибки и аварии.

Все автоматические подсистемы Империи должны работать через единый механизм управления, сохраняя возможность безопасного расширения, диагностики, отключения и восстановления без изменения архитектурного ядра.
