# TACTIC_GUIDE.md

# Task System v3.0

## Руководство для Тактика

---

# 1. Назначение документа

Данный документ предназначен для исполнителя разработки (Тактика).

Он описывает:

- назначение Task System v3.0;
- архитектурные ограничения;
- правила реализации;
- порядок работы с ТЗ;
- критерии готовности изменений.

Документ не заменяет архитектурную документацию.

Основным источником архитектуры являются:

- Task System v3.0 Architecture Specification;
- Task System v3.0 Data Model Specification;
- Task System v3.0 Component Interface Specification;
- Task System v3.0 Roadmap Migration;
- Task System v3.0 Development Rules.

---

# 2. Роли участников

## Координатор

Отвечает за:

- цели проекта;
- принятие решений;
- утверждение изменений;
- управление приоритетами.

---

## Архитектор

Отвечает за:

- проектирование системы;
- подготовку ТЗ;
- контроль архитектуры;
- принятие архитектурных решений.

Архитектор не пишет код реализации.

---

## Тактик

Отвечает за:

- реализацию утверждённых ТЗ;
- внесение изменений в код;
- тестирование;
- подготовку отчёта о выполнении.

Тактик не изменяет архитектуру самостоятельно.

---

# 3. Главная цель Task System v3.0

Task System v3.0 — это центральная система управления Империей.

Это не просто очередь задач.

Она должна обеспечить:

- единое управление задачами;
- единое управление исполнителями;
- централизованные политики;
- контроль выполнения;
- восстановление после ошибок;
- возможность управления без изменения кода.

---

# 4. Основная архитектурная схема

```text
                Control Layer
                      |
                      v
             Empire Dispatcher
                /          \
               v            v
          Scheduler     Feature Switches
               |
               v
          Task Registry
               |
               v
       Assignment Engine
               |
               v
       Executor Registry
               |
               v
          Executors
```

Дополнительные системы:

- Watchdog — контроль;
- Diagnostics — наблюдение;
- Logging — история.

---

# 5. Обязанности компонентов

## Dispatcher

Делает:

- принимает решения;
- обрабатывает события;
- управляет задачами.

Не делает:

- не выполняет работу;
- не управляет крипами напрямую.

---

## Scheduler

Делает:

- определяет разрешённые действия;
- применяет политики.

Не делает:

- не создаёт задачи;
- не назначает крипов.

---

## Task Registry

Делает:

- хранит задачи;
- меняет состояния;
- предоставляет данные.

Не делает:

- не принимает решения.

---

## Assignment Engine

Делает:

- выбирает исполнителя;
- назначает задачу;
- снимает назначение.

Не делает:

- не создаёт политику.

---

## Executor Registry

Делает:

- хранит состояние исполнителей;
- отслеживает жизненный цикл.

Не делает:

- не выбирает задачи.

---

# 6. Правила разработки

## Запрещено

Тактик не должен:

- менять архитектуру без согласования;
- создавать новые управляющие центры;
- создавать отдельные очереди задач;
- создавать отдельные системы управления;
- хранить состояние вне утверждённой структуры Memory;
- связывать компоненты напрямую.

---

## Разрешено

Тактик может:

- добавлять реализацию утверждённых интерфейсов;
- добавлять новые типы задач;
- добавлять новые события;
- добавлять технические функции внутри своего компонента;
- улучшать производительность без изменения архитектуры.

---

# 7. Работа с Memory

Основная структура:

```text
Memory.taskSystem

├── dispatcher
├── scheduler
├── tasks
├── executors
├── events
├── switches
├── diagnostics
└── log
```

Правило:

Если данные относятся к Task System — они должны находиться внутри `Memory.taskSystem`.

---

# 8. Правила выполнения ТЗ

Каждое ТЗ выполняется последовательно.

Перед началом:

1. Изучить цель ТЗ.
2. Проверить архитектурные ссылки.
3. Определить затрагиваемые файлы.
4. Не изменять другие подсистемы без необходимости.

---

После выполнения:

Тактик предоставляет отчёт:

```text
# Отчёт Тактика — ТЗ №XX

## Выполнено

...

## Изменённые файлы

...

## Архитектурное соответствие

...

## Проверка

...

## Возможные проблемы

...
```

---

# 9. Правило одного изменения

Одно ТЗ должно решать одну архитектурную задачу.

Запрещается объединять:

- несколько подсистем;
- несколько архитектурных слоёв;
- несколько независимых изменений.

---

# 10. Совместимость с работающей Империей

Империя работает в реальном времени.

Поэтому:

Запрещено:

- останавливать работающие системы;
- выполнять массовые переписывания;
- удалять старый код без миграции;
- менять несколько критических систем одновременно.

---

# 11. Миграция v2.0 → v3.0

Во время перехода:

Task System v2.0 продолжает работать.

Task System v3.0 внедряется постепенно.

Порядок:

1. Feature Switches.
2. Event Queue.
3. Dispatcher.
4. Task Registry.
5. Executor Registry.
6. Scheduler.
7. Assignment Engine.
8. Watchdog.
9. Diagnostics.
10. Миграция подсистем.

---

# 12. Критерии качества реализации

Изменение считается выполненным, если:

- код соответствует ТЗ;
- архитектура не нарушена;
- система не ломает существующую Империю;
- добавлена диагностика при необходимости;
- есть возможность отключения;
- есть понятный отчёт.

---

# 13. Если обнаружено архитектурное противоречие

Тактик не решает архитектурный вопрос самостоятельно.

Порядок:

1. Остановить спорное изменение.
2. Описать проблему.
3. Передать вопрос Архитектору.
4. После решения продолжить реализацию.

---

# 14. Главный принцип работы

Тактик реализует.

Архитектор проектирует.

Координатор принимает решения.

Task System v3.0 строится постепенно, безопасно и без нарушения работы действующей Империи.

Любое изменение должно делать Империю более управляемой, устойчивой и предсказуемой.
