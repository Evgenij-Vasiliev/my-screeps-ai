## 2. Целевая модель (как должно быть)

Одна величина — **энергия в хранилище комнаты**. От неё зависит, что разрешено. Движение вверх и вниз — с гистерезисом, чтобы не мигало.

### 2.1. Полосы (снизу вверх)

| Полоса склада | Что работает |
| --- | --- |
| **< 165k** | только ядро: добыча, спавн, перенос энергии, терминал; фоновые задачи стоят |
| **165k** | + заправка башен (оборона — последнее, что отключается) |
| **175k** | + ремонт |
| **180k** | + строительство |
| **185k** | + апгрейд контроллера |
| **195k** | + **фабрика** (энергия → батарейки) |
| **210k** | + **рынок: продажа** (в первую очередь батарейки) |
| **225k** | + **рынок: закупки** (только из BUY_LIST) |
| **240k** | + **powerSpawn** |
| **255k** | + **лаборатории** |
| **270k** | + **бусты** |

Порядок выключения при падении — обратный: бусты → лаборатории → powerSpawn → закупки → продажа → фабрика → апгрейд → стройка → ремонт → башни. При падении до 165k остаётся только ядро; до 150k склад не доводим.

### 2.2. Гистерезис
Общий зазор (например, 10–15k): включаем на пороге, выключаем на «порог − зазор». Один параметр на все полосы, чтобы не плодить числа.

### 2.3. Дно
`STORAGE.ENERGY_MIN = 150000` остаётся жёстким дном для забора крипами и в лестнице не участвует. Лестница обязана отключать потребителей **раньше**, чем склад дойдёт до дна.

## 3. Конфиг (constants.js): пороги — данными, не литералами в логике

Один объект, все пороги в одном месте, читаемые имена, абсолютные значения выводятся из базы:

```js
const ENERGY_POLICY = {
  BASE: STORAGE.ENERGY_MIN,      // 150000 — дно, не порог отключения
  HYSTERESIS: 15000,             // общий зазор вниз
  TOWERS_ON: 165000,
  REPAIR_ON: 175000,
  BUILD_ON: 180000,
  UPGRADE_ON: 185000,
  FACTORY_ON: 195000,
  MARKET_SELL_ON: 210000,
  MARKET_BUY_ON: 225000,
  POWER_SPAWN_ON: 240000,
  LABS_ON: 255000,
  BOOST_ON: 270000,
};
```

Правила:
* в коде — **только имена** (`ENERGY_POLICY.FACTORY_ON`), ни одного числа порога в `room.manager`/`task.generators`/рынке;
* менять порог = править одну строку здесь и выгружать;
* проверка конфига тестом: монотонность (каждый следующий порог выше предыдущего), `TOWERS_ON > BASE + HYSTERESIS`, отсутствие дублей.

## 4. Выключатели (systems.js)

`systems.js` остаётся единственным местом «что вообще разрешено», но получает блок участия в авто-лестнице — без порогов:

```js
energyPolicy: true,            // авто-лестница включена
policy: {                      // false — подсистема не участвует, работает по своему тумблеру
  factory: true, marketSell: true, marketBuy: true,
  powerSpawn: true, labs: true, boost: true,
  upgrade: true, build: true, repair: true, towers: true,
},
```

Логика: `systems.<подсистема> === false` → выключено навсегда; `systems.policy.X === false` → не управляется лестницей (работает как раньше); `true` → лестница решает по складу.

## 5. Где живёт логика и что придётся тронуть

**Новый модуль `energy.policy.js`** (аналог `loadShed`, но по складу):
* `level(room)` → полоса, `isOn(room, "factory")` → boolean, `state(room)` → для диагностики;

**Точки применения (минимальные):**
* `room.manager.js` — гейты вызовов генераторов задач (там же, где сейчас `shedHard/shedLite`): башни, ремонт, стройка, апгрейд, фабрика, powerSpawn, лаборатории.
* `empire.js` — рынок (продажа/закупка отдельными флагами).
* `market.manager.js` — разделение «продажа разрешена» / «закупка разрешена».
* `task.generators.js` — **не трогаем** (запрет AGENTS.md): нынешние проверки `ENERGY_LADDER`/`systems` там остаются как второй рубеж, но решение принимает `room.manager` на точке вызова. Если без правки генератора не обойтись — отдельное согласование.

## 6. «Что закупаем — не продаём»

* `MARKET.BUY_LIST` и `MARKET.SELL_LIST` — непересекающиеся списки; `NEVER_SELL` включает всё из `BUY_LIST`.
* Тест-контракт: пересечение пусто; каждый ресурс из `BUY_LIST` имеет потребителя в коде (бусты/лабы/фабрика), иначе он не закупается.
* Продажа включается только на полосе `MARKET_SELL_ON`, закупка — только на `MARKET_BUY_ON` (закупка всегда позже продажи).
