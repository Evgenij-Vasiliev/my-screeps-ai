# Оценка проекта на предмет оптимизации по CPU

**Дата:** 2026-09-27
**Область:** все модули рантайма (`main.js`, `empire.js`, `room.manager.js`, `task.*`, `role.*`, `*.manager.js`, `scanner.js`, `cpuMonitor.js`, `market.manager.js`)
**Метод:** статический анализ потока вызовов и стоимости API-обращений. Профайлер на шарде не запускался — оценки CPU ниже являются расчётными (порядок величины), а не измеренными.
**Время на оценку:** ~9 минут.

---

## 1. Главный вывод

Проект архитектурно аккуратен (слои empire → room → task/role разделены, кэш структур есть, дубли задач отсекаются), но **CPU уходит не на логику крипов, а на три вещи**:

1. **`Game.market.getAllOrders()` внутри вложенного цикла** — самый дорогой вызов, вызывается десятки раз за тик.
2. **Отсутствие heap-кэша (`global`)** — ни одного использования `global.*`; всё статичное (id структур, список комнат, счётчики ролей, стройплощадки) пересчитывается каждый тик из `Memory`.
3. **Раздутый `Memory`** — статичные массивы id, дубли задач у каждого воркера, `towerState`. В Screeps `Memory` десериализуется в начале и сериализуется в конце тика целиком, поэтому стоимость ∝ размеру `Memory`, а не числу записей.

Мониторинг CPU (`cpuMonitor.trackRole` на каждого крипа) сам является измеримой статьёй расходов и мешает измерениям.

## 2. Находки по приоритетам

### P0 — править в первую очередь

#### 2.1. Market Manager: `getAllOrders` в тройном цикле
**Файл:** `market.manager.js:43`, `:100`, вызовы из `:171` и `:188`.

```
for group(4) → for terminal(T) → for resourceType(R) → findBestOrder → getAllOrders(...)
```

`Game.market.getAllOrders()` — один из самых дорогих API-вызовов (порядок 0.05–0.3 CPU при большом ордербуке). Уже при 2 терминалах и ~20 типах ресурсов это **десятки вызовов за тик даже тогда, когда сделок нет** (лимит `MAX_DEALS_PER_TICK` останавливает цикл только после *успешной* сделки, а неудачные попытки сканируют всё).
Оценка: **2–8 CPU/тик** — вероятно, основная статья расходов проекта.

**Что делать:**
- Считать `surplus` **до** обращения к рынку (сейчас `getResourceGroup` + `getReserve` считаются до, а `getAllOrders` — внутри `trySell`, это уже плюс; но перебор идёт по всем ресурсам склада, а не по избыточным).
- Кэшировать ответ рынка на тик: `global.marketOrders[Game.time % N]`, обновлять раз в 10–20 тиков, а не каждый тик.
- Один вызов `getAllOrders({type: ORDER_BUY})` без `resourceType` + группировка в JS — 1 вызов вместо R.
- Рынок вызывать не каждый тик, а `Game.time % 10 === 0`.
- `getEmpireTerminals()` (`:87`) — `Object.values(Game.rooms)` каждый тик; заменить на `global`-кэш имён комнат.

#### 2.2. `cpuMonitor.trackRole` вокруг каждого крипа
**Файл:** `room.manager.js:50`, `cpuMonitor.js:29-38`.

На каждого крипа каждый тик: два вызова `Game.cpu.getUsed()` + создание замыкания `() => {...}`. При 100 крипах это 200 вызовов `getUsed()` и 100 аллокаций closures за тик.
Оценка: **0.2–0.8 CPU/тик** только на измерения + давление на GC.

**Что делать (минимальная правка):**
- Убрать per-creep `trackRole`; оставить замеры на границах подсистем (они уже есть в `runRoom`).
- Если нужна разбивка по ролям — аккумулировать время внутри `runCreepLogic` одним `getUsed()` до/после всего цикла и делить пропорционально, либо включать детальный замер по флагу `Memory.cpuMonitorVerbose` на 1 тик из 100.
- Замыкания заменить на прямой вызов: `trackRole(role, fn)` вызывать без аллокации (передавать саму функцию + аргумент), либо инлайнить замер.

#### 2.3. `cpuMonitor.endTick` — запись в Memory каждый тик
**Файл:** `cpuMonitor.js:41-52`.

`Object.keys(Game.creeps).length` (аллокация массива всех имён) и три записи в `Memory.cpuStats` **каждый тик**. Последнее увеличивает объём `Memory` постоянно.
**Что делать:** держать накопители в `global`, сбрасывать в `Memory.cpuStats` только когда `Game.time % CPU.REPORT_INTERVAL === 0`; число крипов считать только в тик отчёта.

#### 2.4. `role.builder`: полный перебор стройплощадок империи на каждого строителя
**Файл:** `role.builder.js:22-23`.

```js
const sitesInRoom = Object.values(Game.constructionSites).filter(s => s.pos.roomName === creep.room.name);
```

Это O(стройплощадки империи) на **каждого** builder'а каждый тик, с аллокацией массива. При 10 строителях и 200 площадках — 2000 итераций + 10 массивов за тик.
**Что делать:** собрать `roomState.constructionSites` один раз на комнату за тик (см. 2.6) и брать `creep.pos.findClosestByRange(...)`.

#### 2.5. `spawn.manager.countRole`: 9 проходов по списку крипов
**Файл:** `spawn.manager.js:12-24`, вызов в цикле `:47`.

`creeps.filter(...)` на каждую роль из `SPAWN_QUOTA` — 9 проходов с 9 замыканиями на комнату за тик. При этом 6 из 9 квот равны `0` — их считать не нужно.
**Что делать:** один проход с накоплением в объект-счётчик, пропуская роли с `SPAWN_QUOTA[role] === 0`.

#### 2.6. Стройплощадки империи пересканируются на каждую комнату
**Файл:** `task.generators.js:485` (`generateBuildStructures`).

`Object.values(Game.constructionSites).filter(...)` — на каждую комнату за тик, плюс `isDuplicateBuildTask` делает `tasks.some(...)` на каждую площадку → O(площадки × очередь).
**Что делать:** индекс `global.sitesByRoom` (пересобирать раз в тик или по событию), а очередь проверять через `Set` ключей, построенный один раз на тип задачи.

#### 2.7. `detectAttack`: обход всех стен и валов каждый тик
**Файл:** `room.manager.js:69-76`.

Каждый тик на каждую комнату с башнями: `[].concat(walls).concat(ramparts)` (2 аллокации) + `reduce` по всем hits + **запись** `Memory.rooms[room].lastWallHits`. В развитой комнате это 200–500 объектов за тик ради детектора, который имеет смысл раз в ~100 тиков (для этого уже есть `TOWER.HOSTILE_CHECK_INTERVAL`).
**Что делать:** проверять атаку раз в `TOWER.HOSTILE_CHECK_INTERVAL` тиков; в остальные тики опираться на `room.find(FIND_HOSTILE_CREEPS)` (движок кэширует результаты `room.find` в пределах тика — это дешевле, чем JS-обход списка id). Писать `lastWallHits`/`underAttack` только при изменении значения.

#### 2.8. `role.tower` пишет `Memory.towerState[id]` каждый тик
**Файл:** `role.tower.js:12-17`, вызов из `room.manager.js:153`.

На каждую башню каждый тик: создание объекта `Memory.towerState[tower.id]` и запись `state.underAttack`. При этом тот же флаг уже есть в `Memory.rooms[room].underAttack` (`room.manager.js:102`) — состояние продублировано.
**Что делать:** убрать `Memory.towerState` целиком, состояние держать в `global` (или переиспользовать комнатный флаг).

### P1 — структурные, средняя трудоёмкость

#### 2.9. Дубль задачи в памяти каждого воркера
**Файл:** `worker.runner.js:41` — `creep.memory.task = task;`

Полная копия объекта задачи (~80–120 байт) оседает в `Memory.creeps[имя].task`, при том что та же задача уже лежит в `Memory.rooms[room].tasks[type]`. 50 воркеров → ~5 КБ постоянного мусора в `Memory`, который сериализуется каждый тик.
**Что делать:** хранить в памяти крипа только `taskId` + `taskType`; саму задачу резолвить через heap-индекс `global.taskIndex` с ленивым построением из `Memory`.

#### 2.10. Линейный поиск в очередях задач
**Файл:** `task.manager.js:45-56` (`findIndexByTaskId`), `:78` (`getNextTask`), `:112` (`reserveTask`), `:139` (`completeTask`).

- `getNextTask` — O(n) на каждого воркера без задачи каждый тик;
- `reserveTask`/`completeTask` — O(n) + `splice` (O(n) сдвиг);
- воркеры, не нашедшие задачу, ротируют `taskIndex` на 1 и на следующем тику снова сканируют очередь целиком (`worker.runner.js:21-24`).

**Что делать:** `global`-индекс `Map<taskId, task>` + счётчик свободных на тип; инвалидация по dirty-флагу при изменении `Memory`. `completeTask` → `delete` из Map + ленивая компактизация массива раз в N тиков вместо `splice`.

#### 2.11. 11 почти одинаковых `isDuplicate*` функций
**Файл:** `task.generators.js:13, 77, 93, 186, 239, 286, 335, 391, 438, 471, 505`.

Каждая — `tasks.some(...)` с 4-уровневой цепочкой `Memory.rooms && Memory.rooms[roomName] && ...` **внутри** колбэка, то есть на каждый элемент очереди. Суммарно O(кандидаты × очередь) на комнату за тик.
**Что делать:** один хелпер, возвращающий `Set` ключей вида `type|targetId|sourceId|resourceType`, построенный один раз на тип задачи за тик.

#### 2.12. `initRoomTasks` и `TASK_CHAIN.includes` на каждое добавление задачи
**Файл:** `task.manager.js:60-70`, вызов из `addTask`.

`TASK_CHAIN.includes(taskType)` — линейный поиск по 11 элементам, плюс 3 проверки свойств `Memory` — на каждый `addTask`.
**Что делать:** `const TASK_TYPE_SET = new Set(TASK_CHAIN)` на уровне модуля; `initRoomTasks` вызывать один раз на комнату за тик (флаг в `global`).

#### 2.13. `Memory` хранит статику, которую там держать не нужно
**Файл:** `scanner.js:38-56` (`structureCache`), `room.manager.js:131` (`wallThreshold`), `:76` (`lastWallHits`), `:102` (`underAttack`), `role.tower.js:12` (`towerState`), `task.manager.js` (очереди).

`structureCache` содержит `wallIds` / `rampartIds` / `roadIds` — в развитой комнате это 300–600 строк id (~7–10 КБ), которые не меняются тиками и сериализуются каждый тик.
Оценка: **0.3–1.0 CPU/тик на 100 КБ Memory**; основной вклад — именно статика.
**Что делать:** перенести `structureCache`, `towerState`, детектор атаки и очередь задач в `global` (heap), оставив в `Memory` только то, что обязано переживать рестарт (и то — с dirty-флагом). Это самый крупный структурный выигрыш после рынка.

#### 2.14. Кэш структур никогда не обновляется — и это ещё и баг
**Файл:** `scanner.js:14-26`.

`ensureStructureCache` выходит, если массивы `extensionIds/roadIds/wallIds/rampartIds` уже есть. То есть:
- новые extensions/roads/walls, построенные после первого сканирования, **навсегда выпадают** из `roomState` → спавн-менеджер их не заполняет, ремонт их не видит, башни не чинят;
- `constants.js` объявляет `CACHE.REFRESH_INTERVAL: 20`, но он **нигде не используется**.

**Что делать:** инвалидация по `Game.time % CACHE.REFRESH_INTERVAL` в `global` + немедленное обновление по событиям `EVENT_STRUCTURE_BUILT` / при `room.find(FIND_MY_CONSTRUCTION_SITES).length === 0` и изменении `controller.level`.

## 3. Корректность, которая влияет и на CPU

Найдено попутно; каждая из этих проблем либо вызывает лишнюю работу, либо делает расчётную нагрузку бессмысленной.

1. **Дублирование крипов в `roomState.creeps`.** `room.manager.js:309-314` добавляет крипа и по `homeRoom`, и по текущей комнате. Крип, ушедший в удалённую добычу, попадает в два `roomState` и **исполняет логику дважды за тик** (двойной CPU, двойные интенты, конкурирующие задачи). `spawn.manager.countRole` при этом считает его дважды.
   *Правка:* один крип — один `roomState` (приоритет `homeRoom`), а для логики «кто физически в комнате» — отдельный список.

2. **Кэш структур не обновляется** (см. 2.14) — новые extensions/roads/walls/towers не попадают в `roomState` никогда.

3. **`SPAWN_QUOTA`/`TASK_CONFIG`** — 6 из 9 квот равны 0 и 5 из 11 генераторов выключены; мёртвые ветки всё равно исполняются каждый тик (проверка `if (!TASK_CONFIG.x) return` стоит в начале и дёшева — это ок, но `TASK_CHAIN` из 11 типов гоняется воркерами целиком).

4. **`role.mineralMiner`** использует `_.sum(creep.store)` и `Object.keys(creep.store)[0]` каждый тик — дешевле `creep.store.getUsedCapacity()` и явное поле `memory.resourceType`.

5. **`market.manager.js:50`** — `Math.min(...orders.map(...))` разворачивает массив в аргументы; при большом ордербуке это риск переполнения стека и лишняя аллокация. Заменить на цикл.

6. **`.screeps.json` и `tests/` в `.gitignore`, `screeps.token.js` — в репозитории.** Секретов в коде нет, обработка токена сделана аккуратно (env → файл проекта → предупреждение о `~/.screeps.json`). Здесь замечаний нет.

## 4. План действий

### Шаг 1 — измерить (сначала, иначе оптимизация вслепую)
1. Отключить `cpuMonitor.trackRole` вокруг крипов (2.2) — иначе замер искажает картину.
2. Включить `Memory.cpuMonitorVerbose = true` на 1 тик и снять распределение по подсистемам.
3. Снять с шарда `RawMemory.get().length` — это прямой прокси стоимости сериализации `Memory`.
4. Отдельно замерить `Game.cpu.getUsed()` до/после `marketManager.run()` — проверить гипотезу 2.1.

### Шаг 2 — быстрые правки (низкий риск, ~1 вечер)
- 2.1 рынок: throttle + один вызов `getAllOrders` на тик
- 2.2 / 2.3 cpuMonitor: убрать per-creep замеры и еже тиковую запись в `Memory`
- 2.4 / 2.6 стройплощадки: индекс по комнатам в `global`
- 2.5 `countRole`: один проход
- 2.7 / 2.8 детектор атаки и `towerState`: реже и без записи в `Memory`
- 3.1 дублирование крипов в `roomState` (баг + двойной CPU)

### Шаг 3 — структурные (заметная переработка)
- 2.9 / 2.10 / 2.11 / 2.12: индекс задач в `global`, `Set` ключей, O(1) резервация
- 2.13: перенос `structureCache` и очередей в heap с dirty-флагом
- 2.14: инвалидация кэша структур (использовать `CACHE.REFRESH_INTERVAL`)

### Шаг 4 — контроль
- Целевые метрики: `CPU/тик`, `CPU/крип`, `RawMemory.length`, `bucket`.
- Регрессионный прогон `tests/load.shed.test.js` после шагов 2 и 3.
- Правило на будущее: **ни одного `Game.market.*` вне throttle**, **ни одного `Object.values(Game.*)` в per-creep коде**, **`Memory` — только для того, что переживает рестарт**.
