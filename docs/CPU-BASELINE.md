### ⚠️ Поправка к оценке №1: `cpuMonitor.trackRole` на каждого крипа

Замерено: `getUsed()` стоит **0.000244 CPU**. Два вызова на крипа = 0.0005 CPU.

## 6. Технические заметки по замерам

1. **Консольная команда длиннее ~1024 символов молча отбрасывается** (проверено: 1000 символов
   выполняется, 1200 — нет, ответ всё равно `ok`). Все выражения в `scripts/baseline.js`
   держатся короче лимита, а `evalInGame` падает с явной ошибкой, если выражение длиннее.
2. Результат выражения консоли не возвращается через POST — скрипт пишет его во временное
   поле `Memory.__bench_*` и читает через `memory.get`, после чего удаляет.
3. `Game.cpu.getUsed` **нельзя отрывать от объекта** (`const u = Game.cpu.getUsed; u()` →
   `Illegal invocation`) — оборачивается в стрелку.
4. Консоль изредка теряет команду — в `evalInGame` добавлены 3 попытки.
5. Аккаунт играет на **shard3** (не shard0): `cpuShard: {shard3: 20}`.
6. **Обернуть игровой API счётчиком из консоли нельзя** (проверено 28.09.2026, шаг 3):
   консольная команда и код бота исполняются в разных JS-контекстах. Обёртка
   `Game.getObjectById = function (id) { … }`, поставленная из консоли, видна в
   следующей консольной команде (`typeof Game.getObjectById.name === ""`), но
   **ни одного вызова из кода бота не получает** — счётчик в `Memory` не появляется
   за 20 c (≈40 тиков). Следствие: число вызовов API за тик замером из консоли не
   берётся, берётся только цена одного вызова (пачкой, через `Game.cpu.getUsed`).
7. **Консольная команда применяется не сразу**: между отправкой и видимым эффектом
   проходит несколько тиков (наблюдалось 3–6 при `PAUSE_MS` 1.2–1.5 c). Скрипт,
   который ставит флаг и снимает его через паузу, должен учитывать этот лаг —
   `scripts/baseline.js` держит паузу 2500 мс и 3 попытки чтения.

поиска. Частоту пересчётов замером из консоли получить не удалось (см. заметку 6 выше), поэтому

## 14. Авария 29.09.2026: циклический require остановил бота, и правка групп структур

### 14.1 Что произошло

Выгрузка кода варианта B остановила бота целиком. Консоль игры:

```
Error: Circular reference to module 'room.manager'
    at Object.requireFn (<runtime>:21121:19)
    at task.generators:7:34        <- const { getDamagedStructures } = require("room.manager")
    at Object.evalCode (<runtime>:15384:76)
    at Object.requireFn (<runtime>:21106:28)
    at room.manager:14:24          <- require("./task.generators")
```

Причина: `room.manager` подключает `task.generators` (`room.manager.js:14`), а правка
варианта B добавила обратный require `task.generators` → `room.manager`. Node такой цикл
разрешает (возвращает частичный exports), **движок Screeps — нет**: он бросает ошибку на
загрузке, поэтому не работает ни один модуль. Замер живости
(`node scripts/check.shard.alive.js shard3 15`, только чтение Memory через API):

| Признак | t0 | t+15 с | t+45 с |
|---|---|---|---|
| `Memory.cpuStats.count` | 13 | 13 | 13 |
| `Memory._taskIdSeq` | 197698 | 197698 | 197698 |

`Memory` не менялась все 60 секунд наблюдения — код на шарде не исполнялся.
`Memory.cpuStats` успел набрать 13 тиков (average 4.450, bucket 10000, 25 крипов) — это
успешный прогон предыдущей версии, а не работа сломанной.

### 14.2 Исправление

Обратный require убран совсем: числа повреждённых владельческих структур переехали в
сканер (`scanner.js`, `collectDamagedStructures`), а `task.generators` теперь зависит
только от `task.manager`, `scanner` и `constants`. Цикл проверяется механически —
`node scripts/check.require.cycles.js` (31 модуль корня, 61 ребро; на сломанной версии
скрипт печатает `room.manager -> task.generators -> room.manager` и возвращает 1).
Правило добавлено в `AGENTS.md:26-28`.

### 14.3 Правка групп структур (второй замер, раздел 13)

Дорогая часть сборки — не дороги, а группы: резолв 366 объектов стоил **0.12080 CPU/тик**
при нуле повреждённых среди них. Теперь в том же проходе сканера по `FIND_STRUCTURES`
снимаются числа владельческих структур (`damagedStats`: плоский `Int32Array` по stride 3 —
`[typeCode, hits, hitsMax]`, плюс `damagedIds` строками), а объект резолвится только для
той структуры, что реально повреждена.

Схема кэша поднята до **3** (`scanner.js`, `CACHE_VERSION`): старый кэш в heap переживает
выгрузку кода, и без перестройки башни до первого обновления кэша не видели бы повреждённых
spawn/tower/extension вовсе (список строится теперь только по числам).

Что осталось у ленивого пути (`room.manager.js`, `getDamagedStructures`, вызов раз в
`TOWER.REPAIR_INTERVAL` = 15 тиков): резолв повреждённых дорог (их сотни) и резолв единиц
повреждённых групп. Верхняя граница стоимости этого пути — 0.18778 CPU на интервальном тике,
ожидаемая доля на тик — 2/15 от неё.
