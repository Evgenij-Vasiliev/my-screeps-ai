CONTRACT IMPLEMENTATION ROADMAP V1.0
Назначение
Документ определяет стратегию внедрения ARCHITECTURE CONTRACT V3.4 в действующую империю Screeps.
Цель внедрения:
превратить контракт из документа в работающий механизм;
обеспечить автоматическую проверку архитектурных правил;
создать основу для дальнейшей реконструкции империи;
минимизировать риск разрушения существующих подсистем.

Принцип внедрения
Контракт внедряется поэтапно.
Запрещается:
переписывать всю империю одновременно;
внедрять несколько архитектурных реформ за один этап;
менять существующие подсистемы без подтверждённого архитектурного решения.
Каждый этап должен завершаться рабочим результатом.

ЭТАП 1
Перенос владения данными в код
Цель
Создать машинное представление владельцев данных.
Результат
Появляется модуль:
contracts/ownership.js
Содержит:
список владельцев данных;
список разрешённых владельцев памяти;
единый источник истины для Ownership Contract.
Критерий завершения
Система способна ответить:
кто владелец каждого раздела памяти;
какой директор отвечает за данный раздел.

ЭТАП 2
Формирование карты ответственности
Цель
Сопоставить текущие подсистемы с контрактом.
Результат
Для каждой подсистемы определены:
владелец данных;
фактический исполнитель;
используемая память;
уровень соответствия контракту.
Критерий завершения
Существует полная карта ответственности империи.

ЭТАП 3
Внедрение Contract Diagnostics
Цель
Научить империю проверять контракт автоматически.
Результат
Появляется:
ContractDiagnostics
Проверяются:
существование владельца;
корректность структуры данных;
наличие обязательных разделов памяти.
Критерий завершения
Империя публикует отчёт о состоянии контракта.

ЭТАП 4
Внедрение Ownership Audit
Цель
Научить систему выявлять нарушения владения.
Результат
Появляется:
ContractAuditor
Выявляются:
множественные владельцы;
нелегитимные записи;
отсутствующие владельцы.
Критерий завершения
Нарушения контракта автоматически обнаруживаются.

ЭТАП 5
Внедрение Lifecycle Contract
Цель
Зафиксировать жизненные циклы объектов.
Результат
Появляется:
contracts/lifecycle.js
Определяются:
состояния;
допустимые переходы;
запрещённые переходы.
Критерий завершения
Ключевые объекты используют формализованные жизненные циклы.

ЭТАП 6
Интеграция с Directors
Цель
Привязать директоров к контракту.
Результат
Каждый Director:
знает свои зоны ответственности;
публикует диагностику;
предоставляет состояние для аудита.
Критерий завершения
Director Layer работает как единая система управления.

ЭТАП 7
Интеграция с DiagnosticsDirector
Цель
Сделать контракт частью диагностики империи.
Результат
DiagnosticsDirector агрегирует:
нарушения контракта;
проблемы владения;
ошибки жизненных циклов;
рекомендации по исправлению.
Критерий завершения
Контракт становится наблюдаемым объектом.

ЭТАП 8
Интеграция с ConsoleDirector
Цель
Предоставить контроль контракта из консоли.
Результат
Доступны команды:
просмотр владельцев;
просмотр нарушений;
просмотр жизненных циклов;
просмотр состояния контракта.
Критерий завершения
Контракт управляется через консоль.

ЭТАП 9
Contract Recovery
Цель
Научить систему автоматически исправлять нарушения.
Результат
Появляются механизмы:
восстановления состояний;
очистки неконсистентных данных;
исправления зависших объектов.
Критерий завершения
Часть нарушений устраняется автоматически.

Финальное состояние
Контракт существует одновременно в трёх формах.
ARCHITECTURE_CONTRACT.md
Человеческое описание архитектуры.
contracts/\*
Машинное описание архитектуры.
DiagnosticsDirector + ContractAuditor
Автоматическая проверка соблюдения архитектуры.
После завершения дорожной карты контракт становится частью работающей империи, а не только архитектурным документом.
