## 6. Итоговая картина: из чего складывается расход системы задач

Оценка собрана из измеренных частей (разделы 2–4), а не из показаний монитора.
Одна неполная комната (`E35S37`), 26 крипов, 5 своих комнат:

| Статья | Расчёт | CPU/тик |
|---|---|---|
| `getNextTask` воркеров | 3.4 свипа × 0.011 + ~5.5 прямых × 0.005 | ≈ 0.05 |
| `hasDuplicate` + построение Set по очередям | 42.8 × 0.0005 + 7–10 пар × 0.002–0.006 | ≈ 0.04 |
| Построение индекса очередей (`reindex`, 45 очередей за тик) | 45 × ~0.0005 + непустые | ≈ 0.03 |
| Скан генератора `fillSpawnsExtensions` | 1 неполная комната × 0.024 | ≈ 0.024 |
| `getTaskById` + `reserve/complete/remove` + `addTask` | 4.95 × 0.0004 + 1.7 × 0.001 + 1.24 × 0.002 | ≈ 0.007 |
| `compactAll` | 1 вызов/тик | ≈ 0.002–0.012 |
| **Итого** | | **≈ 0.15 CPU/тик** |

При `Memory.cpuStats.average` 1.775–2.60 CPU/тик это **6–8 %** тика (монитор отдаёт
блоку `taskManager` 17.6 % — см. раздел 5).

Где лежит основной потенциал (всё — измеренные цифры, не оценки):

1. **Скан spawn/extension**: 0.0240 → 0.0061/0.0034 CPU на неполную комнату при переходе
   на алиасы `.energy`/`.energyCapacity` — 4–7×, при 5 неполных комнатах это −0.09…−0.10 CPU/тик.
2. **Воркерская сторона**: `creep.store.getFreeCapacity()` читается на КАЖДОГО кандидата
   (0.000485 за вызов), плюс на свипе дальность выбранного кандидата считается дважды
   (`worker.runner.js:82-87` и `:140-164`) — ~0.02…0.04 CPU/тик.
3. **Менеджер**: `hasDuplicate` строит ключ из 4 полей и Set по всей очереди на каждую пару
   (комната, тип) за тик; ключ `room+type` строится на каждый вызов (`task.manager.js:54-98`).
4. **Поведенческий гейт** (требует решения человека): не сканировать spawn/extension, когда
   очередь этого типа уже глубже, чем нужно воркерам (в `E35S37` 18–26 задач при ~3 воркерах).
