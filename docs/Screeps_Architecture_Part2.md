# Screeps — Архитектура зрелой империи

## Часть 2. Энергетическая модель и переход к системе задач

---

# Главная идея

На определённом этапе развития империи происходит важный переход в понимании Screeps.

Новички видят игру как набор крипов.

```text
Harvester
Builder
Upgrader
Hauler
Repairer
```

Зрелая архитектура смотрит иначе:

```text
Энергия
↓
Логистика
↓
Задачи
↓
Исполнители
```

Крипы перестают быть центром архитектуры.

Они становятся исполнителями решений, принятых более высокими уровнями системы.

---

# Что такое комната

Распространённое представление:

```text
Комната = набор крипов
```

Архитектурное представление:

```text
Комната = производственная система
```

Схема потоков:

```text
Источники
     ↓
Добыча
     ↓
Логистика
     ↓
Хранилище
     ↓
Потребители
```

---

# Потребители энергии

Практически все системы комнаты конкурируют за один ресурс.

```text
Storage
   │
   ├─ Spawn
   ├─ Extensions
   ├─ Towers
   ├─ Labs
   ├─ Factory
   ├─ Controller
   └─ Construction
```

Все они потребляют энергию.

---

# Главный вопрос комнаты

Незрелая архитектура задаёт вопрос:

```text
Что должен делать апгрейдер?
```

Зрелая архитектура задаёт другой вопрос:

```text
Куда должна быть направлена следующая единица энергии?
```

Это принципиально иной взгляд на систему.

---

# Энергия как бюджет

Каждая комната обладает ограниченным энергетическим бюджетом.

Пример:

Доход:

```text
20 энергии в тик
```

Расход:

```text
Спавн       6
Башни       2
Апгрейд     8
Стройка    10
```

Итог:

```text
26 > 20
```

Комната расходует больше энергии, чем производит.

Такое состояние неустойчиво.

---

# Основная задача энергетической системы

Энергетическая система должна определить:

```text
Доход
Расход
Запасы
Тенденцию
```

После чего принять решение:

```text
Увеличить доход
или
Снизить расходы
```

---

# Energy State

Для этого вводится состояние комнаты.

Пример данных:

```js
{
    income: 20,
    expense: 26,
    stored: 15000
}
```

После анализа система публикует состояние.

Например:

```text
CRITICAL
LOW
NORMAL
SURPLUS
```

---

# Состояние вместо микроконтроля

Очень важная идея зрелой архитектуры:

Энергетическая система не управляет крипами напрямую.

Она публикует только состояние.

Например:

```js
room.memory.energyState = "LOW";
```

или

```js
room.memory.energyState = "CRITICAL";
```

---

# Политики

Следующий уровень развития архитектуры — политики.

Энергетическая система публикует не команды, а ограничения.

Например:

```js
{
    upgrade: false,
    build: false,
    repair: true
}
```

Это означает:

```text
Апгрейд запрещён
Строительство запрещено
Ремонт разрешён
```

---

# Работа других систем

Системы больше не анализируют энергетику самостоятельно.

Они просто проверяют политику.

Пример:

```js
if (!policy.upgrade) {
  return;
}
```

Таким образом:

```text
Энергетика
      ↓
Политика
      ↓
Системы
      ↓
Задачи
      ↓
Крипы
```

---

# Энергия как управляющий сигнал

В зрелой архитектуре энергия становится не ресурсом.

Она становится управляющим сигналом.

Изменение энергетического состояния автоматически меняет поведение всей комнаты.

---

# Следующий этап — задачи

После отказа от управления отдельными крипами возникает вопрос:

```text
Кто говорит крипам, что делать?
```

Ответ:

```text
Task System
```

---

# Задача как единица работы

Пример:

Логистике необходимо доставить энергию.

Создаётся задача:

```js
{
    type: "transfer",
    from: storage,
    to: extension,
    amount: 50
}
```

---

# Масштабирование

В комнате может существовать одновременно:

```text
100 задач
500 задач
1000 задач
```

Каждая задача описывает работу, которую необходимо выполнить.

---

# Новая модель поведения крипов

Старая модель:

```text
Крип самостоятельно принимает решения.
```

Новая модель:

```text
Крип спрашивает систему:
Есть ли задача?
```

---

# Исчезновение ролей

На раннем этапе существуют роли:

```text
Harvester
Builder
Upgrader
Hauler
Repairer
```

На зрелом этапе появляются исполнители задач.

```text
Task Executor
```

Крип больше не думает.

Он выполняет назначенную задачу.

---

# Второй архитектурный переход

Первый переход:

```text
Крипы
↓
Системы
```

Второй переход:

```text
Роли
↓
Задачи
```

Именно этот переход позволяет масштабировать империю без бесконечного роста сложности кода.

---

# Итоговая схема

```text
Энергия
    ↓
Energy State
    ↓
Policy
    ↓
Systems
    ↓
Tasks
    ↓
Creeps
```

---

# Ключевые выводы

1. Комната — это производственная система, а не набор крипов.

2. Главный объект управления — поток энергии.

3. Энергетическая система публикует состояние комнаты.

4. Политики определяют поведение остальных систем.

5. Системы создают задачи.

6. Крипы выполняют задачи.

7. Масштабирование достигается через переход от ролей к системе задач.

---

# Следующая тема для изучения

Task → Scheduler → Dispatcher → Executor

Именно эта цепочка обычно лежит в основе крупных империй и определяет:

- кто создаёт задачи;
- кто назначает приоритеты;
- кто распределяет работу;
- как задачи получают исполнителей.
