# ТЗ №1 — CPU блока Task System (`taskManager` + `worker`)

- **Дата постановки:** 17.09.2026
- **Основание:** `docs/CPU-PROFILE-ROOM-MANAGER.md`, раздел 6 — «следующая задача: адресный разбор и снижение числа действий крипов, начиная с `miner` …, затем `remoteManager` …, затем Task System». Блоки `miner` (`docs/MINER-CPU-OPTIMIZATION.md`), `remoteManager` (`docs/REMOTE-CPU-OPTIMIZATION.md`), `towers` (`docs/TOWER-CPU-OPTIMIZATION.md`) и `harvester` (`docs/HARVESTER-CPU-REPORT.md`) закрыты — из рекомендации раздела 6 остался **только Task System**.
- **Статус:** ⬜ не выполнено (ТЗ выдано, работа не начата).
- **Цель:** понять, из чего состоит CPU блока Task System (`taskManager` + `worker`), и снизить его **не менее чем на 40 %** без изменения архитектуры (FIFO / Worker / Executor, `docs/TASK_SYSTEM_ARCHITECTURAL_FOUNDATION.md`) и без потери пропускной способности логистики.
- **Область правки (кандидаты):** `task.generators.js`, `task.manager.js`, `worker.runner.js`, `room.manager.js` (блок генерации задач и `runCreepLogic`), `constants.js` (`TASK_CONFIG` только как данные). Всё остальное — вне области.
- **Живой шард:** `shard3`, ветка `test` (`npx grunt screeps`). Замеры — по той же методике, что в ТЗ №0 (профиль `cpuMonitor` + адресные счётчики-обёртки в консоли игры + `screeps-api` для выгрузки).
- **Итоговый артефакт:** отчёт `docs/TASK-SYSTEM-CPU-OPTIMIZATION.md` (структура — как у `MINER-CPU-OPTIMIZATION.md` / `REMOTE-CPU-OPTIMIZATION.md`) + обновлённые статусы в `docs/CPU-PROFILE-ROOM-MANAGER.md` и `docs/PROJECT_AUDIT_AND_ROADMAP.md`.

## 2. Гипотезы, которые обязана проверить задача

Каждая гипотеза проверяется **замером до правки** и фиксируется в отчёте с числом и методом. Правка под гипотезу делается только если она подтвердилась.

| # | Гипотеза | Как проверяем | Признак «подтвердилась» |
| --- | --- | --- | --- |
| H1 | `taskManager` дорог из-за дедупа `some()` по каждой цели | счётчик проходов и сравнённых элементов в `isDuplicate*`; `trackRole("taskGen:<категория>")` | дедуп ≥ 40 % `taskManager` |
| H2 | значимая часть `taskManager` — вызовы, которые заведомо ничего не создадут (категория выключена в `TASK_CONFIG`, или нет `storage`/структур-целей) | под-бакет на каждый из 11 генераторов + счётчик «вышел по ранней причине» (какой именно: флаг / нет storage / нет целей / нет нужды) | ≥ 20 % `taskManager` на такие вызовы |
| H3 | `worker` дорог на idle-тиках обхода цепочки (`taskIndex +1` без задачи) | счётчики «idle-тик» и «тик взял задачу» в `worker.runner` от имени воркера | ≥ 30 % `worker` — idle |
| H4 | заметная доля `worker` — это обход очередей: `getNextTask` + `findIndexByTaskId` + `Game.creeps[reservedBy]` | обёртки `task.manager.*` (вызовы и CPU) | ≥ 30 % `worker` на выбор/резервацию/завершение |
| H5 | «гости» и спавнящиеся крипы тратят CPU впустую | счётчик «роль `worker` запущена дважды за тик» и «тик у `creep.spawning`» | ≥ 5 % `worker` или ≥ 2 % (`taskManager` + `worker`) |
| H6 | мёртвые `reservedBy` удлиняют просмотры и «залипают» как существующие потребности | счётчики «запись с мёртвой резервацией», «Task не найдена в FIFO» (`worker.runner.js:69-79`), «дубль по ключу идентичности» | доля мёртвых записей > 0 % и растёт между окнами |

**Baseline, который надо снять до первой правки** (иначе контрольный замер будет не с чем сравнивать): задачи создано/завершено по категориям на 100 тиков, средние длины очередей, среднее число idle-тиков на воркера на цикл, среднее число «мёртвых» записей.

## 3. Требования к инструментализации (сначала измерения, потом код)

1. **Только существующий механизм.** Замеры — через `cpuMonitor.trackRole` (новые имена блоков: `taskGen:<категория>`, `workerPick`, `workerExec`, `workerFinish`) и через адресные счётчики-обёртки в консоли игры (как в ТЗ №0 и в отчётах по `miner`/`remoteManager`). Никакого второго мониторинга, `console.log` на каждый тик и записи в `Memory` каждый тик не допускаются.
2. **Обязательные счётчики** (heap `global`, снимок раз в 100 тиков, выгрузка `screeps-api`):
   - по каждой из 11 категорий: сколько раз вызван генератор, сколько задач создано, сколько завершено (`DONE`), снято (`SKIP`), сколько вызовов вышло по ранней причине и по какой именно;
   - дедуп: число проходов и число сравнённых элементов (цель × очередь);
   - воркер: idle-тиков, тиков с взятой задачей, `CONTINUE`/`DONE`/`SKIP`, «Task не найдена в FIFO», тиков у `creep.spawning`, тиков двойного запуска роли (гость);
   - очереди: длина по категориям, число записей с `reservedBy`, из них мёртвых (крипа нет в `Game.creeps`), число дублей по ключу `taskType|targetId|resourceType`.
3. **Измерительный слой отключается** одним флагом (`CPU.PROFILE_ENABLED = false`) и после задачи удаляется или оставляется в опциональном виде — решение фиксируется в отчёте (как в ТЗ №0, раздел 2.4).
4. **Окно замера — не меньше 200 тиков на фазу** (текущий тик шарда ~5 с, планировать время). В шапке отчёта указывать `startTick`/`samples`, все `avg` считать как `sum / samples`, доли — от `roomManager` того же окна.
5. **Снимок очередей до/после** (проверка «логистика не сломалась»): длина и содержимое очередей по 5 комнатам, число завершённых задач за окно, суммарная энергия в спавнах/расширениях, `controller.ticksToDowngrade` и `StructureTower.store` по комнатам.

## 4. Разрешённые изменения (кандидаты — делаются только под подтверждённую гипотезу)

| # | Файл | Правка-кандидат | Ожидаемый эффект | Риск |
| --- | --- | --- | --- | --- |
| P1 | `worker.runner.js` | искать задачу по **всей** цепочке за один тик, начиная с `taskIndex` и сохраняя приоритетный порядок; `taskIndex` остаётся точкой старта (задача 2 роадмапа) | воркер не теряет 6–8 тиков на пустые категории → рост пропускной способности, меньше idle-CPU | средний: не сломать приоритеты |
| P2 | `worker.runner.js` | очередь и завершение задачи — по `creep.memory.homeRoom`, а не по `creep.room.name`; не брать задачу, если крип не в комнате очереди (задача 11 роадмапа) | нет «мёртвых» записей с `reservedBy`, короче просмотры очередей | средний: согласовать с §11–13 фундамента (правило «гостя») |
| P3 | `room.manager.js` (`runCreepLogic`) | `if (creep.spawning) continue;` (задача 3 роадмапа) | минус CPU на спавнящихся крипах, задача не блокируется на десятки тиков | низкий |

| P8 | `task.manager.js` | страховка от мёртвых `reservedBy` **существующим механизмом** (проверка `Game.creeps` уже есть в `getNextTask`): счётчик + (только если H6 подтвердится) очистка при переполнении очереди. Новый реестр/TTL-структуру не вводить | очередь не «залипает», просмотры короче | низкий |
| P9 | `room.manager.js` | try/catch вокруг каждого генератора и вокруг `runRoom` (задача 4 роадмапа) | не CPU, а страховка: одна плохая комната/генератор не роняет остальные | низкий |

**Архитектурные границы (нарушать нельзя):**

- не добавлять `scheduler`, `dispatcher`, `assignmentEngine`, `stableMatching`, `priority`, `taskId`, `Task Registry`, глобальную очередь (§21 фундамента);
- не менять принцип «Task остаётся в FIFO до `DONE`/`SKIP`» (§7) и «Executor не создаёт новые Task» (§19);
- не менять состав и порядок `TASK_CHAIN` — это и есть приоритеты;
- вне области: `roomState` (задача 1), Traveler (задача 9), квоты спавна (задача 7), `energySource` (задача 3 аудита — трогать только если замер H3 покажет, что без этого idle-тик не убрать, и отдельным шагом с обоснованием);
- диагностику не удалять: редкий `console.log` об аномалии оставить, но не размножать логи в горячем пути.

## 5. Критерии приёмки и стоп-условия

### 5.1 Основные (обязательные)

| Метрика | Baseline (17.09.2026) | Цель |
| --- | ---: | ---: |
| Task System целиком (`taskManager` + `worker`) | 1.9780 мс/тик (27.5 % `roomManager`) | **≤ 1.20 мс/тик** |
| `taskManager` (генерация) | 1.0172 мс/тик | ≤ 0.55 |
| `worker` (выполнение) | 0.9608 мс/тик | ≤ 0.65 |
| Завершённых задач за окно (все категории) | baseline-число (снять в шаге 1) | **не меньше baseline** |
| Созданных задач за окно (все категории) | baseline-число | не меньше baseline |
| Idle-тиков на воркера на цикл | 6–8 (расчётно; уточнить замером) | ≤ 1 |
| Записей с мёртвой резервацией / «Task не найдена в FIFO» | baseline | не растёт, в идеале 0 |
| Дублей по ключу `taskType\|targetId\|resourceType` | baseline | 0 |

### 5.2 Функциональные («логистика не сломалась», окно ≥ 200 тиков)

- энергия в спавнах/расширениях по каждой из 5 комнат — не ниже baseline (снимок каждые 20 тиков, сравнивать `min` и `avg`);
- `controller.ticksToDowngrade` в комнатах с задачами `upgradeController` — не ниже baseline;
- заливка башен (суммарный `StructureTower.store` или счётчик `fillTowers`) — не ниже baseline;
- терминал: задачи `fillTerminalEnergy`/`fillTerminalResources` создаются и завершаются не реже baseline;
- ни одной «потерянной» задачи: `completeTask`/`removeTask` не возвращают `false` в штатном режиме (счётчик аномалий = 0).

### 5.3 Стоп-условие (немедленный откат шага)

- завершённых задач стало меньше baseline более чем на 5 %;
- появилась мёртвая резервация или дубль задачи;
- в логе появилось `[worker.runner] … Task не найдена в FIFO`;
- энергия в спавнах/расширениях просела более чем на 5 % к baseline;
- `tsc` / `eslint` / `node --check` дают новые ошибки (eslint должно остаться ≤ 16 проблем).

## Приложение B. Почему следующая задача — Task System, и что в неё не входит

1. По разделу 6 `docs/CPU-PROFILE-ROOM-MANAGER.md` порядок был: `miner` → `remoteManager` → Task System. Первые два закрыты, Task System остался. Дополнительно он **единственный блок, который вырос относительно замера ТЗ №0**: `taskManager` 0.9919 → 1.0172, `worker` 0.8355 → 0.9608 (окно с 809 замерами) — при том что `miner` после оптимизации упал (2.29 → ≈1.7).
2. Сейчас Task System — самая крупная группа после ролей-исполнителей: 1.978 мс/тик (27.5 % `roomManager`), при том что из 5 комнат в двух очереди полностью пусты, а 10 воркеров крутят цепочку из 11 типов.
3. В неё **не входят** (и в этом ТЗ не делаются): ленивый `roomState` (задача 1 роадмапа), переделка Traveler и `travelTo`-цены (задачи 9 и вывод отчёта по `remoteManager`, раздел 7), квоты и гейты спавна (задача 7), `energySource` (задача 3 аудита), состояние игры в `Memory` (задача 12), реакция на `bucket` (задача 5).
4. Правило проекта сохраняется: «если решение можно реализовать существующими механизмами без нового архитектурного уровня — используется существующий механизм» (фундамент, §23). Поэтому все кандидаты §4 — это улучшение существующих функций (`Set` вместо `some`, один проход вместо 11, предвычисленный список включённых категорий), а не новые сущности.
