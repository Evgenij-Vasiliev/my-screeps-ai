# ПЛАН ИСПРАВЛЕНИЯ ЭНЕРГЕТИЧЕСКОЙ ЭКОНОМИКИ — 2026-11-15

Основание: аудит `docs/AUDIT-ENERGY-2026-11-15.md`. Режим: проект, без изменений кода.

Пометки: **Факт** — из аудита/кода; **Расчёт** — арифметика; **Гипотеза** — требует замера; **Параметр** — стартовое значение для калибровки.

## А. Предлагаемая модель

Энергия комнаты делится на три слоя:

1. **Неприкосновенный резерв** — `STORAGE.ENERGY_MIN` (150k, факт constants.js:5) + `DEFENSE_RESERVE` (20k). Из него не берёт ни одна задача, кроме аварийного `ignoreReserves`.
2. **Зарезервированная энергия задач** — сумма `reserve` активных задач. Задача не может обещать больше, чем есть сверх резерва. Резерв списывается при постановке задачи и возвращается при завершении/отмене.
3. **Свободный профицит** — `storage.energy − резерв − зарезервировано`. Только он распределяется: инфраструктура → производство → рынок.

Ключевой принцип: `TASK_ENERGY_LIMITS` перестаёт быть «порогом допуска» и становится **контрактом задачи**: `minStorage`, `reserve` (сколько задача вправе забрать), `maxEnergy` (за один рейс), `priority`. Проверка — **при исполнении**, а не только при создании.

Фабрика работает не «потому что склад выше 225k», а потому что:
- есть свободный профицит;
- запас батареек ниже цели;
- продажа батареек экономически оправдана (цена выше порога).

Продажа не привязана к 240k склада: она привязана к **запасу батареек** и цене. Производство и продажа используют один и тот же целевой запас.

## Б. Алгоритмы

### Б.1. Накопление и резерв

```
reserve(room) = STORAGE.ENERGY_MIN + DEFENSE_RESERVE
reserved(room) = Memory.rooms[room].energyReserved  // ведущий счётчик
free(room) = storage.energy - reserve(room) - reserved(room)

canReserve(task, amount):
  free(room) >= amount
  storage.energy - amount >= reserve(room)
```

- `addTask` увеличивает `energyReserved` на `task.reserve`; `completeTask`/`releaseTask` уменьшает. При компакции/удалении — пересчёт по очереди (редко, не каждый тик).
- Задача без `reserve` (например, `fillSpawnsExtensions`) резервирует `min(1600, free)`; если free < 600 — задача не создаётся.
- Аварийные задачи (`spawn` при голоде, `towers` при атаке) имеют `ignoreReserves` и не входят в этот лимит.

### Б.2. Исполнение энергозатратной задачи

В `worker.runner` перед вызовом исполнителя:

```
if (!energyPolicy.canExecute(room, task)) {
  releaseTask(room, task);   // не удалять, а вернуть в очередь
  continue;                  // взять следующую задачу
}
```

`canExecute`:
1. `storage.energy >= task.minStorage`;
2. `storage.energy - reservedByOthers >= task.reserve + reserve(room)`;
3. `task.expiresAt` не истёк (защита от старых задач).

`energySource.withdrawFromStorage(creep, { amount, minStorage })`:
- `amount = min(creep.freeCapacity, task.maxEnergy, task.reserve)`;
- не опускает storage ниже `max(minStorage, reserve(room))`;
- один `withdraw` на рейс, без полного рюкзака «на всякий случай».

Это закрывает три дыры аудита: задача не исполняется после падения склада, не забирает больше бюджета, не конкурирует за один и тот же резерв.

### Б.3. Приоритеты

Сохраняем `TASK_CHAIN`, но добавляем группы:

| Группа | Задачи | priority |
| --- | --- | --- |
| Аварийные | `fillSpawnsExtensions`, `fillTowers` при атаке | 100 |
| Обязательные | `fillTowers`, `fillTerminalEnergy` (до 100k), `collectFactoryBattery` | 80 |
| Инфраструктура | `repairStructures`, `buildStructures`, `upgradeController` | 50 |
| Производство | `fillFactoryEnergy`, `fillPowerSpawnEnergy` | 40 |
| Рынок | `marketSell`, `marketBuy` | 30 |

Порядок в `TASK_CHAIN` остаётся; `priority` используется при выборе задачи, если в очереди несколько типов (worker.runner берёт задачу с максимальным priority, затем по порядку цепочки). Это не новый Scheduler — только поле у существующих задач.

### Б.4. Фабрика и батарейки

Условия запуска одной партии (600 энергии → 50 батарей):
1. `batteryStock(room) < BATTERY_STOCK_TARGET`;
2. `free(room) >= FACTORY_BATCH_ENERGY + FACTORY_SAFETY` (600 + 600);
3. `storage.energy >= FACTORY_START` (200k) — нижняя страховка, не главный критерий;
4. `factory.cooldown === 0`;
5. цена батареи не ниже `BATTERY_MIN_MARGIN` (после калибровки).

Интенсивность и глобальный лимит:
- не больше **одной партии за 10 тиков** на комнату (кулдаун движка);
- задача `fillFactoryEnergy` несёт `maxEnergy = 600`; воркер везёт ровно 600, а не 1600;
- после партии `factoryNextBatchAt = Game.time + 10`; следующая задача создаётся только после этого и при выполнении условий;
- **глобальный лимит активных фабрик**: `MAX_ACTIVE_FACTORIES = clamp(floor(estSurplusPerTick / 60), 0, 5)`, где `estSurplusPerTick` — оценка имперского профицита по дельте суммы Storage за 100 тиков. Пока истории нет — стартовое значение 1. Право на партию получают только `MAX_ACTIVE_FACTORIES` комнат с наибольшим `free(room)`; остальные ждут. Это не Scheduler: решение считается в `energy.policy` по существующим комнатам и кэшируется на тик.

Остановка:
- `batteryStock >= BATTERY_STOCK_TARGET` → производство пауза, продажа приоритетна;
- `storage.energy < FACTORY_STOP` (180k) → пауза до восстановления;
- свободный профицит < 600 → пауза;
- `MAX_ACTIVE_FACTORIES === 0` (профицит отрицательный) → все фабрики на паузе.

`factory.manager` вызывает `produce` только если `energyPolicy.factoryAllowed(room)`; это проверка на **уровне производства**, а не только заливки.

### Б.5. Продажа батареек

- `batteryStock = storage.battery + terminal.battery` по комнате; империя — сумма.
- Продажа при `batteryStock >= BATTERY_SELL_TARGET` (20 000 империя, 4 000/комната) **и** `terminal.battery >= BATTERY_SELL_BATCH` (1 000).
- Цена: `order.price >= BATTERY_MIN_PRICE`; порог калибруется по фактической цене (см. §В, данные).
- Приоритет продажи выше производства: если сток выше цели, `factoryAllowed = false`.
- Комиссия `calcTransactionCost` списывается из энергии терминала и учитывается в `energySpent` комнаты; если после сделки терминал ниже 100k — сделка откладывается до доливки.
- `marketBuy` не трогаем до отдельного решения; текущий `systems.policy.marketBuy = false`.

### Б.6. Терминалы и межкомнатное распределение

- Терминал — буфер 100–150k, не потребитель склада. Цель 150k сохраняется.
- `fillTerminalEnergy` — только до 150k; после этого задача не создаётся.
- `balanceEnergy`: донор — комната со `storage.energy > TRANSFER_FLOOR` (250k) и терминалом > 110k; получатель — `storage.energy < TRANSFER_LOW` (150k). Передаётся столько, чтобы донор остался ≥250k, получатель поднялся до 150k; комиссия входит в расчёт.
- Если донор ниже 250k — энергия не передаётся; ресурсы (KH/UO) могут передаваться, но их комиссия списывается с энергобюджета комнаты.
- Никаких новых менеджеров: используются `terminalNetwork.balanceEnergy` и `send`.

## В. Числовые параметры

| Параметр | Значение | Обоснование |
| --- | ---: | --- |
| `STORAGE.ENERGY_MIN` | 150 000 | существующий пол; факт |
| `DEFENSE_RESERVE` | 20 000 | 4 башни × 1 000 запас + ремонт; Параметр |
| `TASK_MAX_ENERGY.factory` | 600 | одна партия; расчёт 600 → 50 |
| `TASK_MAX_ENERGY.terminal` | 1 000 | один рейс, не опускать терминал; Параметр |
| `TASK_MAX_ENERGY.tower/repair/build/upgrade` | 500 | 1 WORK, малые партии; Параметр |
| `FACTORY_START` | 200 000 | резерв 170k + 30k буфер; Параметр |
| `FACTORY_STOP` | 180 000 | гистерезис 20k; Параметр |
| `FACTORY_SAFETY` | 600 | ещё одна партия в запасе; Параметр |
| `BATTERY_STOCK_TARGET` | 20 000 империя | текущий сток 71 200 → сначала продать; Параметр |
| `BATTERY_SELL_TARGET` | 20 000 | тот же; продажа до цели |
| `BATTERY_SELL_BATCH` | 1 000 | комиссия не съедает смысл; Параметр |
| `BATTERY_MIN_PRICE` | калибровка | нет данных о цене; измерить `getAllOrders` |
| `TRANSFER_FLOOR` | 250 000 | донор сохраняет резерв; Параметр |
| `TRANSFER_LOW` | 150 000 | получатель не ниже пола; Параметр |
| `FACTORY_BATCHES_PER_10_TICKS` | 1 | кулдаун движка; факт |
| `MAX_ACTIVE_FACTORIES` | 1 старт, далее floor(профицит/60) | нет истории профицита; калибровка |

Расчёт баланса: добыча 100/тик − крипы 28.4 − инфраструктура ~10 − резервный запас = свободный профицит ~60/тик. Одна партия 600 раз в 10 тиков = 60/тик — ровно один активный завод. Второй завод допускается только при профиците >120/тик, иначе производство ставится на паузу. Это не «повышение порога», а бюджет: производство не может обещать больше свободного профицита.

## Д. Последовательность внедрения

**Этап 1. Единая политика и контракт задачи (без изменения поведения).**
- `constants.js`, `energy.policy.js`, `task.types.js` (поля задачи).
- Цель: `TASK_ENERGY_POLICY` — единственный источник; `ENERGY_LADDER`/`BANDS` — только диагностика.
- Проверка: тесты политики; сравнение поведения на 200 тиках.
- Откат: вернуть коммит.

**Этап 2. Резервирование и execution-time проверка.**
- `task.manager.js`, `worker.runner.js`, `energySource.js`, `task.executors.js`.
- Цель: задача не исполняется ниже `minStorage`; `energyReserved` не превышает free.
- Проверка: тест «задача создана при 225k, склад упал до 160k → release»; `Memory.rooms[].energyReserved` сходится.
- Откат: отдельный коммит.

**Этап 3. Фабрика по бюджету и стоку.**
- `factory.manager.js`, `task.generators.js`.
- Цель: одна партия 600, `maxEnergy=600`, пауза при стоке > цели.
- Проверка: 100 тиков — число партий = floor(профицит/600); сток не растёт выше цели.
- Откат: отдельный коммит.

**Этап 4. Продажа и учёт комиссии.**
- `market.manager.js`.
- Цель: продажа от 20k стока, не от 240k склада; комиссия в бюджете.
- Проверка: сток 71.2k → продажи; кредиты растут, энергия терминала не ниже 100k.
- Откат: отдельный коммит.

**Этап 5. Терминальная сеть.**
- `terminalNetwork.js`.
- Цель: энергия идёт только от донора >250k к получателю <150k; комиссия учтена.
- Проверка: нет передач при доноре <250k; получатель не ниже 150k.
- Откат: отдельный коммит.

**Этап 6. Калибровка.**
- 500–1000 тиков: storage trend, партии/тик, продажи/тик, комиссии.
- Параметры `BATTERY_MIN_PRICE`, `FACTORY_START/STOP`, `TRANSFER_FLOOR` — по замеру.
- Критерий: storage растёт ≥20/тик в среднем за 1000 тиков; сток батарей ≤20k; продажи >0; инфраструктура не голодает (очереди repair/towers не растут).

## Е. Ожидаемый результат

1. **Положительный баланс.** Обязательные 150k + 20k резерв; свободный профицит ~60/тик. Фабрика получает 600 только при свободном профиците, не чаще 1 партии/10 тиков; вторая фабрика — только при профиците >120/тик.
2. **Рост Storage.** Пока сток батарей выше цели, фабрики не пополняются; свободный профицит идёт в склад. После продажи стока и восстановления склада производство возобновляется.
3. **Устойчивая работа фабрик.** Одна партия за 10 тиков на комнату, ровно 600 энергии; нет «залипания» 40k в фабрике; нет простоя из-за того, что задача не создана, — создаётся по бюджету.
4. **Реализация батареек.** Продажа при стоке ≥20k и приемлемой цене; комиссия учитывается; производство останавливается, если сток не реализуется.
5. **Рост кредитов без истощения.** Кредиты растут от продаж, но энергобаланс контролируется отдельно; рост кредитов не считается доказательством — критерий ещё и storage trend.

## Данные, которых не хватает

- Фактическая цена батарейки и энергетическая цена сделки (`getAllOrders`/`calcTransactionCost`).
- История storage по тикам и счётчики «пришло/ушло» по подсистемам.
- Энергия, потраченная `terminalNetwork.send` и `market.deal`.
- Возраст/просрочка задач в очередях.

До калибровки `BATTERY_MIN_PRICE` и `FACTORY_START/STOP` — параметры, а не факты. Без счётчиков этапы 3–5 проверяются косвенно (storage trend, сток, число партий, продажи).
