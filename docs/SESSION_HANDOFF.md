Почему фабрика выше башен, PowerSpawn и терминала: энергия — один ресурс на всё,
и считается цена энергии в каждом потребителе: фабрика 54,2 кредита/энергию
(600 → 50 battery по 650), PowerSpawn 50 (50 энергии → 1 power ≈ 2500),
терминал 0 (лежит мёртвым грузом). Батарея вывезена вперёд снабжения, потому что
**полная фабрика не может варить** (`used − components + amount > capacity`).

Почему апгрейд и стройка в конце — и почему контроллер при этом не теряется:
`generateUpgradeController` создаёт задачу только при
`ticksToDowngrade < CONTROLLER.DOWNGRADE_MIN` (50k), исполнитель снимает её на
`DOWNGRADE_MAX` (150k). То есть это ПОДДЕРЖАНИЕ уровня, а не рост: комната платит
воркерами только когда запас на даунгрейд кончился. Отдельного аларма по
контроллеру в проекте НЕТ (`CONTROLLER` читают только генератор и исполнитель) —
если апгрейд начнёт задерживаться, это будет видно только по
`Memory.rooms[*].tasks.upgradeController` и по падению `ticksToDowngrade`.

### 0.2 `executeFillTerminalEnergy` — найденная по дороге реальная ошибка

`TERMINAL_SUPPLY.ENERGY_MIN` (100000→**10000**) в появлении задачи НЕ участвует
вовсе: генератор (task.generators.js:263) сравнивает с `ENERGY_TARGET`. ENERGY_MIN
— это пол остатка терминала-донора в `terminalNetwork.fitSendAmount` и в
`balanceEnergy`; при 100000 терминал был НЕДОСТИЖИМЫМ донором
(`terminalEnergy > 100000 + 1000` при живой энергии 6.8–26.5k), то есть обычная
балансировка не отправляла ничего. Теперь один энергопол на три механизма:
`TERMINAL_SUPPLY.ENERGY_MIN` = `TERMINAL_NETWORK.PRIORITY_ENERGY_FLOOR` =
`MARKET.BUY_ENERGY_FLOOR` = 10000.

`ENERGY_TARGET` 150000→**20000** — это НЕ подбор числа. Исполнитель
останавливался на `isTargetFull(target)`, то есть лил терминал до ПОЛНОЙ ёмкости
300k, тогда как генератор считал потребностью разницу до ENERGY_TARGET. Теперь
исполнитель тоже останавливается на цели (до и после переноса). Главный
предохранитель от обесточивания комнаты — не эти числа, а гейт
`storage > STORAGE.ENERGY_MIN × 1.3` (195000) в генераторе И в исполнителе.

## 1. Что починено в системе бустов (проверено живьём)

`boost.manager.js`:
- `available()` считает запас **суммой** источников (лаба + storage + terminal + реакторы троек),
  с досрочным выходом по `minStock` (CPU не вырос).
- `runDelivery` клампит `withdraw` не только по свободному рюкзаку, но и по **запасу источника**
  (движок не выдаёт частично → был shuttle «терминал ↔ лаба»).
- Признак «буст уже выдан» считается **по телу** (`rowSatisfied`): свойства `creep.boosts` в движке
  **НЕТ** (проверено: `typeof === "undefined"`). Частичный буст дотягивается до квоты строки.
- **Аварийная правка (после инцидента):** рейс за бустом **не начинается**, если лаба занята другим
  минералом; груз **сбрасывается** (`dropCarriedBoost`) во всех путях отмены процедуры
  (конфликт минерала, `MAX_BUSY_TICKS`, энергопауза, нет строки политики, `cap = 0`).
  Причина инцидента: miner с 3 CARRY получал в рюкзак 150 единиц буста, лаба его не принимала →
  рюкзак занят на 100 % → добыча вставала, линки не разгружались, спавны пустели.
- Метрика `Memory.__boostMetric` различает: `no stock` / `бусты выданы` / `partial X` /
  `boost abandoned` / `лаба занята X` / `ждём очистки лабы`.

`terminalNetwork.js`: `availableToGive` считает запас донора **вместе с лабораториями**
(симметрия с `collectLabRequests`), иначе у производителя KH2O излишек был ровно нулевым.

Константы: `LAB_KEEP` 3000 → **1000**; `PRIORITY_ENERGY_FLOOR` и `BUY_ENERGY_FLOOR` 20000 → **10000**
(при 20000 отправлять/покупать могла одна комната из пяти; терминалы держат 6.8–26.5k).
