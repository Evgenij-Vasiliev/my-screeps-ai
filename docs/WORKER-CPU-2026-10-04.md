## 1. Главный вывод

**Цифра «worker тратит 0.9 CPU/тик» была артефактом замера, а не расходом воркеров.**

На шарде стоял включённый флаг `Memory.cpuMonitorVerbose = true` (`room.manager.js:79-96`):
он заставляет `cpuMonitor.trackRole` мерить КАЖДОГО крипа КАЖДЫЙ тик, тогда как
штатное расписание — 1 тик из `CPU.VERBOSE_INTERVAL = 97` (`constants.js:509`).
Поролевая цифра `Memory.cpuStats.subsystems.worker` — это замер с надетым на него
измерительным прибором.

| Окно (по 240 с), `scripts/worker.cpu.ab.js` | avg тика | роль `worker` в `subsystems` |
|---|---|---|
| A: `cpuMonitorVerbose = true` | **3.685** CPU/тик | **0.65 – 1.13** CPU/тик |
| B: `cpuMonitorVerbose = false` | **3.417** CPU/тик | **0.13** CPU/тик |

Снятие флага: −0.268 CPU/тик на империю (7.8 % расхода) и −0.5…−1.0 CPU/тик
в самой цифре роли. Причина в `cpuMonitor.js:141-152`: `trackRole` = два
`Game.cpu.getUsed()` (0.000198 CPU каждый, замер §4) + замыкание на вызов;
при 5 воркерах это ≈0.0015 CPU/тик сверху — но `startTick` с этим флагом ещё и
переводит ВЕСЬ профиль в режим «мерить всегда», а внутри `worker.runner`
добавляются свои `getUsed()` (`worker.runner.js:433,441,477,481`).

## 2. Сколько на самом деле стоят воркеры

Контекст на момент замера: лимит 20 CPU, bucket **10000 (полный)**, 20–22 крипа,
5 комнат, роли `worker`=5, `miner`=6, `linkWorker`=5, `labWorker`=5.

| Источник | Что даёт | Значение |
|---|---|---|
| `Memory.cpuStats.average` | расход империи | 3.42 – 3.85 CPU/тик |
| `Memory.cpuStats.subsystems.worker` (verbose выключен) | роль worker | 0.13 CPU/тик |
| бортовой `global.__workerDiag` (`worker.runner.js:404-485`) | 3.95 вызова исполнителя/тик, 0.188 CPU на вызов | 0.5 – 0.9 CPU/тик |

50-м тике (`SAMPLE_EVERY = 50`, `worker.runner.js:99`), поэтому 113 тиков окна
ловят 1–2 замера. Оценка §2 — не цифра, а диапазон; точная цифра роли —
поролевая, **0.13 CPU/тик** (без надетого профиля).

## 4. Где у воркеров реальные потери

Бортовой счётчик за окно 113 тиков (`scripts/worker.diag.delta.js`):

| Метрика | Значение | Комментарий |
|---|---|---|
| решений | 446 = **3.95/тик** | исполнитель вызывается 3.95 раза за тик на империю |
| из них без задачи (`noTask`) | 119 = **26.7 %** | воркер потратил тик и работы не нашёл |
| построений индекса комнаты (`scans`) | 125 | почти столько же, сколько `noTask` |
| «сухих» выходов (`dryExits`) | **0** | правило 2 из `worker.runner.js:40-42` НЕ срабатывает ни разу |

`dryExits = 0` при 125 построениях индекса — это и есть измеренная
неэффективность: признак «в комнате работы нет» живёт один тик
(`worker.runner.js:153-177`, ключ `Game.time`), поэтому каждый тик каждая
безработная комната перебирает все 11 очередей заново
(`buildIndex`, `worker.runner.js:258-295`). Цена этой работы мала
(`cpuTask` = 0.015 CPU на решение, §3: примитивы дешёвые), но она повторяется
20 000 раз (`scans` = 19 617 с момента старта VM) и не даёт ничего.

## 5. Что предлагается (по одной правке, каждая — отдельное согласование)

Все правки ниже лежат в `worker.runner.js` / `task.manager.js` — то есть в
файлах из `AGENTS.md:8-10`, менять их можно только отдельной командой человека.
Порядок — по отношению «экономия / риск».

1. **Снять постоянный профиль.** `Memory.cpuMonitorVerbose = false` (или удалить
   флаг). Экономия **≈0.27 CPU/тик (7.8 %)**, риск нулевой, кода не касается.
   Точка отката: `Memory.cpuMonitorVerbose = true`.

   **СДЕЛАНО 04.10.2026, `Game.time` = 83419237** (отдельная команда человека),
   одной консольной командой, без выгрузки кода. Проверка после правки
   (`api.memory.get` на shard3, `cnt` = 51):
   `cpuMonitorVerbose = false`, `bucket = 10000`, `avg` = 4.077 CPU/тик,
   `worker = undefined` (поролевая цифра больше не собирается — это и есть
   признак снятого флага: ключ `worker` в `subsystems` писался только веткой
   профиля по крипам, `cpuMonitor.js:244-246`), `labManager` 0.522,
   `terminalNetwork` 0.515 — подсистемы продолжают мериться штатно.
   Откат одной командой: `Memory.cpuMonitorVerbose = true`.
2. **Признак «комнатa без работы» — на несколько тиков.** Если `buildIndex`
   вернул `count === 0`, запомнить это в heap на `N` тиков (например, 5) вместо
   одного, и не перестраивать индекс, пока признак жив. Ожидание — до 0.05
   CPU/тик; требует замера после правки, потому что появление работы должно
   снимать признак немедленно (иначе воркер простоит лишние тики).
3. **Не мерить то, что не спрашивали.** `worker.runner.js` берёт `getUsed()`
   при `cpuSample`; это диагностика, а не работа. Замер оставить, но вынести
   под флаг (`Memory.cpuWorkerDiag`), как сделано для `cpuGenProfile`
   (`room.manager.js:811`). Экономия — доли процента, зато исчезает риск
   забыть флаг и мерить постоянно (ровно то, что случилось с `cpuMonitorVerbose`).

**Что делать НЕ надо (проверено):**

- Оптимизировать поиск задачи и резолвы внутри исполнителей — там 0.0005 CPU
  на вызов (§3), это шум.
- Менять движение: `creep.move` 0.0009 CPU (§3), живой кэш пути 0.0117 CPU
  (`docs/move-cost-measure.json`), пересчёты 0.0714 CPU/тик на всю империю
  (шапка `task.executors.js:40-44`). Порт Traveler ради CPU уже пробовали —
  снижения нет (`task.executors.js:24-39`).
- Трогать состав флота: квота `worker: 1` на комнату уже стоит
  (`constants.js:121`), а `AGENTS.md:7` запрещает массовые операции над флотом.
